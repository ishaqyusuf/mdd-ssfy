## Question

What durable archive evidence, list-row presentation, cache invalidation,
projection versioning or backfill, mobile behavior, and regression proof are
required so archive and restore remain attributable and consistent across every
consumer of the shared Sales Orders query?

## Comments

> *This was generated by AI during Wayfinder issue commenting.*

**Proposed answer:** Persist archive state on the authoritative Sales Order and
add an index supporting type/deletion/archive/date list selection. Keep archive
state out of the compact projected row payload unless presentation proves it
necessary: canonical ID selection already enforces scope, and changing the
order revision makes existing projections refresh safely. Show the Archived
query chip and Restore action rather than adding a redundant badge to every
row. Archive/restore invalidates default and archived lists, summaries,
saved-tab counts, and related Sales Order caches. Validate at the highest
seams: command authorization/idempotency/audit tests; default/archived/bin list
and summary contract tests; legacy/projected parity tests; filter/action UI
tests; and one authenticated browser smoke covering archive, disappearance,
Archived discovery, and restore.

**Why:** This preserves the guarded read-model contract while avoiding an
unnecessary projection migration.

**Assumptions / risk:** No projection version bump or bulk deployment-time
archival is needed unless implementation proves the archive state must enter
the row payload.
