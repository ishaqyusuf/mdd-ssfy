# Define Canonical Square Payment Identity

Type: grilling
Status: closed
Blocked by: 01, 02
Parent: [`../map.md`](../map.md)

## Question

How should GND persist and resolve the actual refundable Square tender payment
id across payment-link, Terminal, and card flows; distinguish it from local
Square rows, Square order ids, payment-link placeholders, and Terminal checkout
ids; safely recover eligible existing payments; and prevent a refund from ever
targeting an identifier unrelated to the selected Sales payment?

## Comments

> *This was generated by AI during Wayfinder issue commenting.*

**Proposed answer:** Give every refundable Square tender its own canonical
provider identity. Store the actual Square `Payment.id` separately from GND's
local payment row ID, Square order ID, payment-link ID, and Terminal checkout
ID. A customer transaction may reference multiple Square tenders, but every
refund targets exactly one verified tender.

Capture the tender ID during payment-link and Terminal settlement instead of
discarding it. Refund commands must accept a local payment reference only; the
server resolves and verifies the Square payment ID, status, amount, currency,
location, and relationship to the selected Sales payment. Never accept a
client-supplied provider ID.

For existing payments, recover tender identity through Square order or
Terminal checkout reads. Persist it only when the match is unique and verified
against amount, currency, location, time, and local payment relationships.
Ambiguous records enter Finance review and remain non-refundable through GND.
Preserve the overloaded legacy `SquarePayments.paymentId` as a compatibility
value until migration rather than changing its meaning in place.

**Why:** This establishes the trustworthy provider identity required before a
refund can be submitted.

**Assumptions / risk:** Historical payments may lack enough evidence for
automatic recovery; those records must remain manually reviewable rather than
being guessed.

### Resolution

Implemented `SquareTenderPayment` with the actual Square `Payment.id`, separate
legacy/link/order/Terminal checkout references, settlement-time capture for
payment links and Terminal, and server-side tender resolution. Ambiguous
historical identities remain in Finance review and cannot be guessed.
