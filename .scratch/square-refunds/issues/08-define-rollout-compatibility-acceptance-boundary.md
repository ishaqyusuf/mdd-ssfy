# Define Rollout Compatibility And Acceptance Boundary

## Question

What schema/API compatibility, legacy-path retirement, webhook rollout,
historical reconciliation-report boundary, sandbox and production fixtures,
failure drills, observability, migration gates, and end-to-end acceptance proof
must be complete before Square Refunds for Sales can ship?

## Comments

> *This was generated by AI during Wayfinder issue commenting.*

**Proposed answer:** Ship behind a server-side Square Refund feature gate plus
`can.editRefundSquare`. Deploy durable refund, allocation, provider-event inbox,
transition, and projection storage before enabling commands. Deploy and verify
the webhook receiver before subscribing production events.

Cutover requirements:

- Capture canonical Square tender IDs in every new payment path.
- Recover historical identities only when uniquely verifiable.
- Route all Square refund attempts through the new command.
- Make legacy `resolvePayment` reject Square methods so it cannot create a
  second provider refund.
- Project completed refunds into required compatibility reads until Finance
  and Sales use the canonical projection.
- Provide a read-only historical provider-versus-GND reconciliation report
  without bulk allocation.

Acceptance must cover full/partial refunds, link/Terminal/card payments,
multi-order allocations, C.C.C/tip rules, pending reservations, direct
completion, failures, rejection, timeout retry, duplicate/out-of-order
webhooks, external refunds, fulfilled-order Finance exceptions, unauthorized
access, immutable completion, document refresh, and notification idempotency.
Complete sandbox automation, failure drills, one controlled low-value
production refund, pending-age monitoring, reconciliation alerts, and rollback
instructions before general enablement.

**Why:** This defines a reversible cutover that prevents the legacy
false-completion path from coexisting with the new workflow.

**Assumptions / risk:** Production proof requires an intentionally created
low-value completed Square payment and explicit operator approval; no existing
customer payment should be used as a test fixture.

### Resolution

Implemented the server feature gate, dedicated permission, additive schema,
canonical tender capture, legacy Square-refund rejection, compatibility
projection, focused failure/idempotency tests, responsive authenticated QA, and
a real completed `$1.00` sandbox payment/refund. Production enablement and its
separately approved low-value proof remain deployment operations.
