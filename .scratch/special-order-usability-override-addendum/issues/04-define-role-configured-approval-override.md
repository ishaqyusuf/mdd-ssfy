# Define Role-Configured Special Order Approval Override

Type: grilling
Status: open
Blocked by: None
Parent: [`../map.md`](../map.md)

## Question

How should Role configuration grant `Override Special Order Approval`, which
unapproved states and operation categories may it bypass, how must it compose
with existing operational permissions, and what server-side decision metadata,
Sales Activity, and audit evidence must distinguish an override from an ordinary
allow, warning, or block?

## Comments

> *This was generated by AI during Wayfinder issue commenting.*

**Proposed answer:** Add **Override Special Order Approval** to Role
configuration with normalized scope `overrideSpecialOrderApproval`; Super Admin
receives it through existing implicit permission behavior. The server reads the
capability from the authenticated session, never from client input.

The capability supplements the employee's existing purchasing, production,
packing, or dispatch permission. It bypasses the Special Order gate for
Signature Pending and Reapproval Required progression across all four operation
categories. It does not override Customer Declined, grant an underlying
operational permission, or affect recovery operations.

Return an explicit `OVERRIDDEN` decision and record actor, role, order,
revision, operation, enforcement mode, source, and timestamp. Sales Activity
may deduplicate repeated notices while durable operational audit evidence
remains attributable. Staff UI shows that approval was overridden.

**Why:** Role configuration grants the requested exception while preserving
least privilege and a server-authoritative audit trail.

**Assumptions / risk:** Role-permission changes follow the project's existing
session-refresh behavior.
