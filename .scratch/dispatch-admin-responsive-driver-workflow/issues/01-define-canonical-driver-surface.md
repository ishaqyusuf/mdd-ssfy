# Define The Canonical Driver Surface

Type: grilling
Status: open
Blocked by: None
Parent: [`../map.md`](../map.md)

## Question

Should the phone-first responsive website become the canonical driver surface,
remain a parity fallback beside Expo, or own only warehouse packing while Expo
continues trip execution? Define authentication, assigned-work scoping,
supported phone/browser baseline, offline expectations, installability, and the
conditions under which either existing surface can be retired.

This decision must explicitly reconcile the new responsive-web request with
ADR-054, which currently names Expo as canonical.

## Comments

> *This was generated by AI during Wayfinder issue commenting.*

**Proposed answer:** Make the phone-first responsive website the long-term
canonical driver surface, but only after a controlled parity pilot. Expo remains
canonical during implementation and becomes the temporary fallback after the
web pilot succeeds. Record the eventual authority change in a new ADR rather
than silently contradicting ADR-054.

Use ordinary employee authentication and server-enforced assigned-driver
scoping. Support the current and previous major Android Chrome and iOS Safari
versions. Make the experience installable as a PWA without requiring
installation. Cache the manifest and unfinished forms for recovery, but require
fresh server confirmation for packing, trip start, proof, and completion; stale
or offline state must never authorize a transition.

Retire Expo only after assigned-work parity, camera/signature behavior,
weak-network recovery, proof completion, accessibility, usage, and reliability
acceptance gates pass.

**Why:** This supports the requested simple responsive workflow while
preserving the accepted authority until the replacement is demonstrated.

**Assumptions / risk:** Browser camera, signature, background recovery, and
weak-network behavior may not achieve Expo parity without targeted device
validation, so canonical ownership cannot change at build completion alone.
