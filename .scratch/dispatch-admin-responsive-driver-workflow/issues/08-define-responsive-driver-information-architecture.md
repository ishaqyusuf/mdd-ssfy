# Define The Responsive Driver Information Architecture

Type: grilling
Status: open
Blocked by: 01, 05, 06
Parent: [`../map.md`](../map.md)

## Question

What phone-first responsive information architecture gives the driver a clear
assigned-work dashboard, warehouse packing journey, permission-request state,
ready-to-move queue, ongoing delivery, destination details, proof capture, and
completed history? Define navigation, next-action hierarchy, list/card detail,
touch and viewport constraints, error/retry states, and how the same pages
adapt to tablet and desktop without exposing admin-only controls.

The answer should preserve the useful behavior already present in the mobile
driver flow while removing mobile-only assumptions.

## Comments

> *This was generated by AI during Wayfinder issue commenting.*

**Proposed answer:** Use a phone-first driver shell with four destinations:
Today, Assigned, Active delivery, and Completed. Today is the default dashboard
and ranks work by overdue, scheduled time, packing readiness, and route start.
Each card shows order/customer, destination, due window, item count, readiness,
and exactly one primary next action.

Opening assigned work leads to a short sequence: Review load, Pack items,
Report blocker when needed, Wait for admin or continue, Confirm load, Start
trip, capture proof, Complete delivery. The blocker form should prefill the
dispatch/item context and ask only blocker type, available quantity, note, and
optional photo. While waiting, the driver can work another assignment and gets
a prominent ready-to-resume notification when the server revalidates the item.

Tablet and desktop may widen the list/detail layout but must expose the same
driver-scoped data and actions, never admin controls.

**Why:** This keeps the driver experience fast and obvious while covering the
full warehouse-to-delivery loop without calls to the office.
