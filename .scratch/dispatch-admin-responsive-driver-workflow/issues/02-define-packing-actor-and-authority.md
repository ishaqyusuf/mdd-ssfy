# Define Packing Actor And Execution Authority

Type: grilling
Status: open
Blocked by: None
Parent: [`../map.md`](../map.md)

## Question

When an assigned driver arrives at the warehouse and verifies the load, is the
driver acting under a packing capability, a delivery capability, or an explicit
combined role? Decide whether the responsive driver journey presents the
existing Packing List commands in context, deep-links to Packing List, or needs
a new presentation over the same server authority. Define who may pack,
re-open, correct, or finalize an assigned dispatch and what happens when a
driver changes after packing.

The answer must avoid creating a second packing truth beside the accepted
Packing List and dispatch-bound inventory commands.

## Comments

> *This was generated by AI during Wayfinder issue commenting.*

**Proposed answer:** Give an assigned driver an explicit, assignment-scoped
packing capability and present a simplified packing journey inside the driver
experience, backed by the existing Packing List and dispatch inventory commands.
Do not create a second packing state machine and do not make a Packing List
document the default order-row destination.

The assigned driver may verify and finalize only the active dispatch assigned
to them. A warehouse/admin capability owns corrections and reopening. If the
driver changes after packing begins, require an audited handoff and revalidation
of the current packed quantities before the replacement driver can continue.

**Why:** Drivers get one simple workflow while the accepted packing authority,
inventory effects, permissions, and audit trail remain intact.
