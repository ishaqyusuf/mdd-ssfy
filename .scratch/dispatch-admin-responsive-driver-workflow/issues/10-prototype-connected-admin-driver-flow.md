# Prototype The Connected Admin And Driver Flow

Type: prototype
Status: open
Blocked by: 07, 08, 09
Parent: [`../map.md`](../map.md)

## Question

Does one low-cost connected prototype make the complete critical path obvious
to both office admin and driver: assign order, open assigned work, verify and
reduce quantities, request permission, approve or deny, finish packing, start
delivery, capture signature/proof, and observe fulfillment? Prototype the
desktop admin and narrow responsive driver states with realistic dense data,
then record the human feedback and interaction decisions required by the final
specification.

The prototype is a decision artifact, not production code, and must expose
blocked, denied, partial, retry, and success states rather than only a happy
path.

## Comments

> *This was generated by AI during Wayfinder issue commenting.*

**Proposed answer:** Build one non-production connected prototype with a dense
desktop admin state and a 390px-wide driver state sharing the same realistic
fixture. Demonstrate admin assignment; driver review and partial packing;
structured blocker reporting; in-app/email notification representation; admin
resolve and deny outcomes; driver ready-to-resume feedback; load confirmation;
trip start; arrival; proof capture; completion; and the final Fulfilled or Back
order result.

Include blocked, denied, physical-shortage, partial, stale-revision,
weak-network retry, duplicate-submit, reassignment, and successful paths. Test
with representative office admins and drivers. Record whether they can identify
the single next action without coaching and correctly explain Status, Assigned
To, Packing blocked, Back order, Delivered, and Fulfilled. Use their observed
confusion to settle interaction and terminology decisions before the final
specification.

The prototype must use simulated state and perform no production API, email,
inventory, dispatch, or proof writes.

**Why:** One connected artifact validates the handoff between admin and driver,
including unhappy paths that separate screen mockups would hide.

**Assumptions / risk:** Prototype usability does not prove server correctness,
permissions, email delivery, offline recovery, or inventory safety; those remain
implementation acceptance gates.
