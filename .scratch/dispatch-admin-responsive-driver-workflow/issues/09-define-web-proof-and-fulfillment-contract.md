# Define Web Proof Completion And Fulfillment Contract

Type: grilling
Status: open
Blocked by: 01, 05
Parent: [`../map.md`](../map.md)

## Question

How should the responsive website capture recipient identity, signature,
photos, notes, completion type, arrival evidence, and failed-delivery reasons
while preserving the existing resumable and idempotent proof contract? Define
browser storage/recovery, weak-network behavior, request identity, upload
limits, retry messaging, permission checks, and the precise distinction between
Delivered and Fulfilled.

The answer must keep final inventory consumption and fulfillment on the server
and must not treat a client-side success screen as terminal evidence.

## Comments

> *This was generated by AI during Wayfinder issue commenting.*

**Proposed answer:** Reuse the existing resumable
`completeDispatchWithProof` contract for the responsive website. Keep one
request ID while the completion form is active and bind it to the proof
fingerprint. Require recipient identity and completion type, require signature
for a delivered completion unless an explicit policy exception applies, and
allow up to five validated photos under the existing size and MIME limits.
Persist arrival evidence, note, failed-delivery reason, and optional
purpose-limited location metadata; location is evidence, never authorization.

Use a user- and dispatch-scoped browser draft for recovery, with server-staged
documents and completion metadata remaining authoritative. Purge the browser
draft after success, logout, reassignment, or expiry. Byte-equivalent retries
resume the same request; reusing its identity with different proof conflicts.
Keep the form and proof mounted after weak-network failure and show an explicit
retry/sync state. Close it only after the server confirms completion.

`Delivered` means valid proof was accepted for that dispatch. `Fulfilled` means
the server also completed canonical inventory effects and aggregate order
evaluation confirms no remaining fulfillment demand. A browser success screen
cannot produce either state independently.

**Why:** Web and Expo share the same safe retry, permission, document, and
inventory-finalization behavior instead of creating a weaker browser path.

**Assumptions / risk:** Browser storage of signatures/photos requires bounded
retention and identity isolation, and camera/background behavior needs real
device testing.
