## Highest-Risk Findings

- P1 - Generic public task execution still allows arbitrary Trigger task names and payloads. Evidence: `apps/api/src/trpc/routers/task-trigger.route.ts` exposes `trigger` and `status` as `publicProcedure`; `trigger` accepts `taskName: z.string()` and `payload: z.any()`, while `status` returns run output and error. Mobile still uses this path for packing through `apps/mobile/src/hooks/use-task-trigger.ts` and `apps/mobile/src/features/dispatch/api/use-dispatch-packing.ts` with `taskName: "update-sales-control"`. For warehouse/driver staff, this undermines accountability for packing/dispatch side effects.
- P1 - Public scheduler controls remain able to update and run task events. Evidence: `apps/api/src/trpc/routers/task-events.route.ts` keeps `list`, `get`, `update`, `history`, `runNow`, `runTest`, and `runStatus` on `publicProcedure`. The dashboard task-events UI consumes those controls. This is a production-operations risk because scheduled payment, reminder, inventory, and dispatch work should require explicit admin authority.
- P1 - Payment and Square terminal side-effect routes are still public. Evidence: `apps/api/src/trpc/routers/checkout.route.ts` exposes checkout initialization, quote acceptance, checkout-link creation, payment verification, and `generateDeviceCode` as `publicProcedure`; `apps/api/src/db/queries/checkout.ts` creates Square device codes with a fixed terminal name; `apps/api/src/trpc/routers/square-test.route.ts` exposes a public terminal checkout test for any supplied device id; `apps/api/src/trpc/routers/customer.route.ts` exposes `getCustomerPayPortal` publicly. Customer payment surfaces need signed, purpose-limited boundaries separate from staff terminal setup.
- P2 - Public internal reads and unscoped office management remain broad. Evidence: `apps/api/src/trpc/routers/filters.route.ts` exposes customer, dispatch, employee, inbound, inventory, job, sales-order, sales-quote, accounting, project-unit, and production filters publicly; `apps/api/src/db/queries/organization.ts` exposes organization list/create as `publicProcedure` and uses `findMany({})` without tenant/office scoping. Brain already has office scoping and SaaS tenancy plans, so this should be treated as a known prerequisite for commercialization.
- P2 - Settings Active Sessions still gives false security. Evidence: `apps/dashboard/src/components/user-logged-in-devices.tsx` renders hard-coded `mockDevices` and the logout handler only waits 500ms with `TODO: Implement actual logout logic.` This can train admins to believe device revocation exists when it does not.

## Worker Usability Review

Special Order handling is now much more trainable: staff get a clear order-level classification and downstream gates rather than relying on memory for non-returnable work. That is a meaningful improvement for sales reps, production coordinators, warehouse staff, and dispatch.

The remaining worker usability issue is hidden authority. Mobile packing can show familiar buttons, spinners, and retries while still routing through a generic task trigger. A warehouse worker should not need to understand background task names or failure output; the server should expose narrow actions such as pack selected items, mark unavailable, and complete pickup/delivery with clear proof requirements.

Active Sessions is the sharpest admin-facing trust issue. A mock device list with a fake logout action creates an attractive but inaccurate security control.

## Customer And Dealer Experience Review

Dealer next-step guidance is implemented in `apps/dealership/src/lib/dealer-next-step.ts`, and it distinguishes request review, payment due, preparation, ready, and fulfilled states. That is good for customer/dealer trust because dealers see what GND is doing next instead of guessing.

The remaining dealer/customer gap is proof and specificity. Dealers can see guidance, but there is still room for a shared timeline that shows manufacturing readiness, payment, packing, pickup/delivery proof, and customer-balance status in one place. For door manufacturing, the most valuable dealer-facing clarity is not generic progress; it is whether dimensions, swing/handing, profile, supplier, special-order acknowledgment, and delivery/pickup readiness have cleared.

Payment trust remains exposed by public checkout and pay-portal routes. Signed links are appropriate, but they should be purpose-limited and separated from staff terminal/device setup and test routes.

## Door-Manufacturing Workflow Gaps

- Manufacturing preflight is implemented for internal Sales Overview, but dealership/mobile surfaces still need a simple cross-surface door-readiness language: dimensions, hinge/swing/handing, profile, supplier, special-order approval, inventory allocation, and PDF readiness.
- Inventory cutover is still not release-clean while repairs are stopped by user request. That means production and warehouse teams should not be trained to trust every inventory projection without visible proof status.
- Packing and dispatch proof is improving, but mobile warehouse packing still depends on a generic task runner. Door-shop workers need scan/photo/signature actions that feel like the task itself, not a background job wrapper.
- Payment and fulfillment states still span multiple systems. Customer/dealer messaging should make it obvious whether GND payment, customer balance, production, packing, and pickup/delivery are each waiting, ready, blocked, or complete.
