## Highest-Risk Findings

### P0 - Public Generic Task Launcher Can Start Arbitrary Trigger.dev Tasks

Evidence: `apps/api/src/trpc/routers/task-trigger.route.ts:5-49`.

The router uses `publicProcedure`, accepts `taskName: z.string()` and `payload: z.any()`, calls `tasks.trigger(params.taskName, ...)`, and returns detailed run status including output and error by run id. Mobile dispatch packing still consumes this generic route through `apps/mobile/src/hooks/use-task-trigger.ts` and `apps/mobile/src/features/dispatch/api/use-dispatch-packing.ts`.

Operational impact: a door manufacturing system needs task starts such as packing, inventory sync, sales history, and notifications to be permissioned, typed, and actor-bound. A generic public launcher makes it hard to prove who started work, whether a payload was valid for that workflow, and whether sensitive run output leaked.

Tracking label: New candidate. The API hardening plan exists, but this exact typed protected task-command registry should be tracked separately before implementation.

### P1 - Public Square Terminal Side Effects Still Exist

Evidence: `apps/api/src/trpc/routers/checkout.route.ts:43-47`, `apps/api/src/db/queries/checkout.ts:1298-1318`, and `apps/api/src/trpc/routers/square-test.route.ts:5-36`.

`checkout.generateDeviceCode` is public and creates a Square Terminal device code with a hard-coded device name. `squareTest.test` is public and creates a $10.00 terminal checkout for any supplied device id. Recent payment and refund work is stronger, but these terminal setup/test routes still cross a payment-provider boundary without the same protected operational guard.

Operational impact: terminal setup and test charges affect customer trust, payment reconciliation, and support load. These should be Super Admin or payment-admin tools with audit evidence, not public procedures.

Tracking label: Plan exists. Payment checkout expansion and API hardening are already present, but this route family should be explicitly swept during the next API boundary pass.

### P1 - Public Sales Mutations And Broad Reads Remain In Revenue Paths

Evidence: `apps/api/src/trpc/routers/sales.route.ts:1320-1393` still exposes public `quotes`, `salesPayWithWallet`, `startNewSales`, `resolvePayment`, `restore`, product/accounting reads, supplier writes, and step metadata writes. `apps/api/src/trpc/routers/sales.route.ts:952-958` also leaves `getOrders` and `getOrdersSummary` public.

Operational impact: sales reps, office staff, and managers need confidence that order creation, restoration, wallet settlement, supplier edits, payment resolution, accounting reports, and quote lists are scoped to the authenticated employee/dealer/customer context. Public routes weaken accountability and make training harder because UI permissions no longer clearly match server authority.

Tracking label: Plan exists. `.brain/plans/2026-07-23-api-public-route-hardening.md` is implemented for many operational routes, but this remaining sales route sweep is still needed.

## Worker Usability Review

Production worker modernization is active and has recently improved tabs, calendar parity, compact controls, and worker-specific submissions. That work fits mixed-skill production staff well because it narrows the visible controls to assigned work.

The remaining usability problem is inconsistency between polished role-specific surfaces and older generic controls. Mobile dispatch packing can complete useful actions, but it still goes through a generic task trigger and appears to rely on manual quantity interactions before proof. Inventory/admin surfaces still include old debug or legacy pathways in places, which increases training burden.

## Customer And Dealer Experience Review

Customer-facing payment/refund work has improved. Square refunds are no longer a top unresolved implementation risk based on `.brain/tasks/done.md`.

Dealer next-step guidance is materially better: approved orders distinguish GND payment from the dealer's customer receivable and avoid promising readiness without explicit fulfillment status. The gap is now the next layer of communication: manufacturing readiness and fulfillment proof are not yet exposed in the same simple dealer language.

Client-ready delivery status is approved as docs work, but not yet part of the daily operational surfaces. That means completed work can still be technically recorded in Brain without automatically giving the customer/dealer a concise "ready, unverified, blocked, next action" update.

## Door-Manufacturing Workflow Gaps

- Quote/order readiness needs one shared door-manufacturing validator for size, swing/handing, profile coefficient, supplier pricing, special-order policy, tax/profile state, production due date, and document readiness.
- Dealer order detail should expose a compact manufacturing-readiness summary after GND approval, not only payment and fulfillment status.
- Inventory allocation should remain a release gate before broader customer/dealer readiness claims.
- Mobile packing should support scan/photo-first proof for pick, pack, load, delivery, and pickup handoff.
- Public route cleanup should prioritize any path that can change production, inventory, payment, supplier, or sales state.
