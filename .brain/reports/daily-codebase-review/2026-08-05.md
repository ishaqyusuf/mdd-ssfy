## Highest-Risk Findings

P1 - Generic background task execution remains public. `apps/api/src/trpc/routers/task-trigger.route.ts:6` exposes `trigger` as `publicProcedure`, accepts arbitrary `taskName` plus `z.any()` payload at lines 8-16, and returns Trigger run status including output/error through the public `status` query at lines 21-46. Inference: this is high risk because inventory, sales history, notification, and fulfillment tasks can affect operational state or reveal diagnostic details.

P1 - Scheduled task-event controls remain public. `apps/api/src/trpc/routers/task-events.route.ts:19-67` exposes list/get/update/history/runNow/runTest/runStatus through `publicProcedure`. The `update` mutation can change event status/filter, and `runNow`/`runTest` can execute scheduled event behavior. This conflicts with the task diagnostics plan's Super Admin/admin-only intent.

P1 - Office organization management remains public and incomplete. `apps/api/src/db/queries/organization.ts:4-27` uses `publicProcedure` for list and create, returns soft-deleted organizations via `findMany({})`, reports `employeesCount: 0`, accepts client-controlled `primary`, and returns `{}` after creating. This exactly matches the risk described in `.brain/plans/2026-07-29-feature-office-organization-management-and-scoping.md`.

P1 - Customer payment surfaces still have public trust boundaries. `apps/api/src/trpc/routers/customer.route.ts:58-61` exposes `getCustomerPayPortal` publicly, while `apps/api/src/trpc/routers/sales.route.ts:1133-1146` leaves `salesPayWithWallet` and `resolvePayment` public. `createPaymentLink` is now protected, which is an improvement, but public account-number/phone-style payment context remains risky for customer privacy and payment integrity.

P2 - Inventory correctness and fulfillment release proof are still not clean. Brain records repairs as stopped by user request, with the last refresh showing unresolved missing/stale/componentless/reconciliation drift state. Today's progress adds mobile backorder/partial-delivery parity, but device/runtime proof is blocked by the shared `@gnd/errors` runtime resolution issue.

P2 - The new shared error package appears mismatched for runtime bundling. `packages/errors/package.json:12-14` exports TypeScript source, while `packages/errors/src/index.ts:1-11` and `packages/errors/src/classify.ts:1-7` import sibling modules with `.js` specifiers. Brain progress says Android export for the new mobile fulfillment slice is blocked on `@gnd/errors` `./app-error.js` resolution. Inference: this can block mobile worker proof and any production bundle that consumes the package through a stricter resolver.

P2 - Settings Active Sessions is visible but mock-backed. `apps/dashboard/src/app/(sidebar)/settings/profile/page.tsx:21-24` renders `Active Sessions`, while `apps/dashboard/src/components/user-logged-in-devices.tsx:9-24` hard-codes two fake devices and `apps/dashboard/src/components/user-logged-in-devices.tsx:35-39` simulates logout with a timeout and TODO. This can mislead admins/users during account-security incidents.

P3 - Payment processor code still carries debug/mock terminal state in operational UI. `apps/dashboard/src/components/widgets/sales-payment-processor/sales-payment-processor.tsx:146-183` uses account-number fallback, public pay-portal data, `console.log(data.error)`, and `mockStatus` state in the payment processor. This is lower than the API-boundary issue but should be cleaned before finance/payment rollout.

## Worker Usability Review

Production, warehouse, driver, and office users benefit from recent improvements: mobile dispatch proof is retryable, mobile fulfillment queues now have a parity slice, and backorder/partial-shipment workspaces are now present in web and mobile. The main usability gap is confidence: blocked typecheck/runtime proof means workers still cannot rely on the new mobile fulfillment surfaces as proven production tools.

The public task controls also create a training and accountability problem. A mixed-skill office team should see named business actions with clear eligibility, not generic task/event controls that can run or reconfigure background work without a visible ownership model.

Active Sessions currently looks like a security feature but is not real. For office/admin staff, mock rows are worse than absence because they imply a logout capability that cannot help during a lost-device or suspicious-login report.

## Customer And Dealer Experience Review

Dealer quote-to-order approval, locked request states, internal/customer print modes, and next-step guidance are now strong tracked areas. The dealer experience should next focus on fulfillment confidence: visible pickup/delivery readiness, proof, remaining backorder, and production readiness should be easy to understand without calling the office.

Customer payment still needs a sharper boundary. Public pay portal and wallet/payment resolution routes should move toward signed checkout tokens, customer authentication, or staff-only workflows depending on the surface. The current split, with some payment link creation protected but related payment context still public, is confusing and increases privacy/payment risk.

## Door-Manufacturing Workflow Gaps

- Manufacturing preflight exists internally through Sales Overview, but dealer/customer-facing preflight is still thin. Dealers would benefit from pre-request checks for dimensions, swing, hinge/profile selections, supplier pricing, and production blockers before a quote becomes an approval request.
- Inventory-backed fulfillment now models backorders and partial shipments, but release confidence depends on proving the runtime path and closing inventory correctness gates. Door manufacturing workflows rely on accurate stock, inbound, production, and delivery state.
- Mobile workflows need scan/photo quick actions for warehouse and field proof. Dispatch proof has photo/signature support, but barcode/QR scanning across backorder, packing, pickup, delivery, and inventory receiving is still a practical opportunity.
