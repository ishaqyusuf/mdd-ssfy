- P1 - Generic public task execution still allows arbitrary Trigger task names and payloads. Evidence: `apps/api/src/trpc/routers/task-trigger.route.ts:6` exposes `trigger` as `publicProcedure`; lines 9-10 accept `taskName: z.string()` and `payload: z.any()`; lines 21-47 expose public run status, output, and error. Mobile warehouse packing still routes through this generic path with `taskName: "update-sales-control"` in `apps/mobile/src/features/dispatch/api/use-dispatch-packing.ts:81`. For warehouse/driver staff, this weakens auditability and makes a high-impact operation depend on a broad task runner.
- P1 - Public scheduler controls remain able to update and run task events. Evidence: `apps/api/src/trpc/routers/task-events.route.ts:19`, `:31`, `:53`, `:58`, and `:67` keep list, update, run-now, run-test, and run-status controls on `publicProcedure`. Evidence: `apps/api/src/trpc/routers/checkout.route.ts:18-47` exposes checkout initialization, quote acceptance, checkout-link creation, payment verification, and `generateDeviceCode` as `publicProcedure`; `apps/api/src/trpc/routers/square-test.route.ts` also exposes a public terminal checkout test for any supplied device id. Customer payment links can be public when signed and purpose-limited, but staff terminal setup/test paths should not share that trust boundary.
- P2 - Public internal reads and unscoped office management remain broad. Evidence: `apps/dashboard/src/components/user-logged-in-devices.tsx:9` renders hard-coded `mockDevices`, and `:35-39` simulates logout with a timeout plus `TODO: Implement actual logout logic.` This can train admins to believe device revocation exists when it does not.

## Worker Usability Review

Special Order handling is now much more trainable: reps explicitly classify orders, customers approve a governed revision, and downstream purchasing/production/packing/dispatch gates can explain why work is blocked.

The remaining usability problem is hidden authority. A warehouse worker can press a concrete packing action, but the implementation still becomes an arbitrary `update-sales-control` background task. Workers should see narrow actions such as pack selected, short item, substitute, photo proof, and complete, while the server enforces the exact allowed command.

Active Sessions is an admin training hazard. A realistic table with fake devices and fake logout is worse than no feature because office staff may believe security cleanup happened.

## Customer And Dealer Experience Review

Dealer next-step guidance is implemented and should be preserved. It gives dealers clearer answers about request review, payment, preparation, pickup/delivery readiness, and completion without inventing unsupported fulfillment states.

The next dealer/customer gain is proof specificity. Dealers and customers need a compact readiness timeline that makes manufacturing facts visible: dimensions, swing/handing, profile, supplier, Special Order approval, payment, packing, pickup/delivery proof, and remaining balance. This should extend the existing dealer guidance rather than create a second progress model.

Payment trust still needs sharper separation between public signed customer flows and staff-only terminal/device setup.

## Door-Manufacturing Workflow Gaps

- Internal Sales Overview has a production preflight for dimensions, handing/swing/no-handle, customer profile/tax, supplier variants, inventory, fulfillment, and document readiness in `packages/sales/src/sales-overview-production-preflight.ts`. Dealership and mobile should reuse the same readiness language.
- Inventory cutover remains not release-clean while repairs are stopped by user request. Production and warehouse users need visible proof status and should not be trained to treat every inventory projection as authoritative.

- Payment, customer balance, production, packing, and delivery states still span multiple systems. The product should make each state visibly waiting, blocked, ready, or complete.
