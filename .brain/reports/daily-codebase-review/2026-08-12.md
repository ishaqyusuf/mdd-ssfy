## Executive Summary

This was a read-only operational codebase review for the GND monorepo using the Africa/Lagos date. The workspace still uses `.brain/` as the active Brain directory; there is no top-level `brain/` directory. The requested `apps/www` and `apps/expo-app` scope maps to the current `apps/dashboard` and `apps/mobile` workspaces, which were reviewed along with `apps/dealership`, `apps/api`, and the requested shared packages.

The strongest current risk is narrower than prior reports but still high impact: dispatch routes themselves are now protected, but generic public task execution remains available through `taskTrigger`, and mobile warehouse/dispatch packing still depends on that generic task path. That means task execution and task-status disclosure remain a cross-surface control boundary instead of a typed, permission-scoped operational command contract.

Dealership quote-to-order approval has improved: direct dealer conversion is now server-retired, quote edit locks are represented in the dealer UI, and the DB query layer throws a locked-edit error for pending/approved/rejected requests. The remaining dealer risk is product/experience completeness rather than an obvious approval bypass.

Customer payment and public quote-acceptance flows remain sensitive. The public checkout router is token-driven and partly expected, but it returns rich order/customer/payment context and can create Square links, verify payments, and accept quotes into orders. That boundary needs ongoing hardening and operational proof because mistakes here directly affect revenue, privacy, customer trust, and fulfillment readiness.

- P1 - Generic public task execution still bypasses typed operational command boundaries. Evidence: `apps/api/src/trpc/routers/task-trigger.route.ts:6` exposes `trigger` as `publicProcedure`, accepts arbitrary `taskName` and `payload`, and calls `tasks.trigger`; `apps/api/src/trpc/routers/task-trigger.route.ts:21` exposes run status with output and error. `apps/mobile/src/hooks/use-task-trigger.ts:62` consumes this route, and `apps/mobile/src/features/dispatch/api/use-dispatch-packing.ts:81` uses it for `update-sales-control` packing operations. Inference: even with protected `dispatch.route.ts`, mobile packing still relies on a broader public task path with a weaker contract.
- P1 - Task Events administrative controls are still public. Evidence: `apps/api/src/trpc/routers/task-events.route.ts:18` through `:76` expose list/get/update/history/runNow/runTest/runStatus through `publicProcedure`. These routes can modify schedule status, run tasks, run tests, and poll status. Operational impact: office/admin task controls can affect inventory imports, reports, and recurring operations, so they need Super Admin or explicit operational permission gates.
- P1 - Public checkout and quote acceptance carry rich customer/payment actions. Evidence: `apps/api/src/trpc/routers/checkout.route.ts:18` through `:47` exposes initialize checkout, quote acceptance, quote accept, checkout-link creation, payment verification, and device-code generation as public procedures. `apps/api/src/db/queries/checkout.ts:305` returns order id, due, customer id, sales rep id, customer phone/email/name/address, and meta for tokenized checkout; `apps/api/src/db/queries/checkout.ts:500` can accept a quote and create an order. This is likely partly intentional, but it remains a high-trust token boundary requiring strict expiry, token scope, replay/idempotency, and monitoring.

## Worker Usability Review

- Sales and office staff get stronger protected dispatch APIs now, but the mixed task-control surface is still hard to train: a manager sees protected dispatch screens while mobile packing quietly uses generic background task execution.
- Warehouse/driver flows need one obvious command path for pack, start, complete, and retry. The current mobile `useDispatchPacking` path builds task payloads client-side and waits on generic status polling, which makes failure explanations depend on Trigger status rather than a domain-specific packing response.
- Inventory operators still need simple, review-safe language around the stopped repair state. The Brain state is explicit; product surfaces should avoid implying the cutover is clean until Phase 8 reconciliation and Phase 10/11 proof gates close.
- Office administrators cannot use Active Sessions for real accountability because the table is currently mock-backed.

## Customer And Dealer Experience Review

- Dealer approval improved materially: direct conversion is retired in `apps/api/src/trpc/routers/dealer-portal.route.ts:388`, and quote lists show locked edit actions when `editLocked` is true.
- Customer checkout and quote acceptance are useful but sensitive. Public token flows should make expiry, order scope, amount, accepted state, and contact data exposure obvious and auditable.
- Dealer next-step guidance is tracked and present, but dealer/customer delivery proof should continue moving toward a timeline that shows order approved, GND balance due/paid, production/packing, ready for pickup/delivery, and completed proof without internal jargon.

## Door-Manufacturing Workflow Gaps

- Production readiness preflight is tracked and implemented in the sales package, but the highest-value next gap is making the checks visible at the right handoff moments: dimensions, handing/swing/no-handle choice, profile/pricing snapshot, supplier variant price evidence, shipping readiness, inventory sync, and document readiness.
- Mobile packing still needs allocation-bound pick work and structured manifest details to be the source of truth for workers: item type, dimensions, handing, ordered/packed LH/RH quantities, SKU/variant, and inventory readiness.
- Barcode/scan-to-pack remains a practical opportunity. I did not find an existing concrete implementation plan for scan-based packing; driver-platform and inventory-item dashboard plans mention scan-friendly work, but not a dedicated barcode execution workflow.
