## Highest-Risk Findings

### P1 - Public Square test route can create terminal checkout side effects

Evidence: `apps/api/src/trpc/routers/square-test.route.ts` still defines `test: publicProcedure`, calls `squareClient.terminal.checkouts.create`, accepts caller-provided `deviceId`, and is mounted in `apps/api/src/trpc/routers/_app.ts` as `squareTest`.

Operational risk: a test endpoint that can create real Square Terminal checkouts should not be publicly mounted in a production API tree. For sales reps and office staff, this can create confusing payment artifacts; for customers, it weakens trust in payment controls.

Tracking status: residual from API hardening coverage, but this exact retirement/protection remains a new daily-report candidate unless Ishaq promotes it into the queue.

### P1 - Public sales, checkout, and customer payment routes still cross money and customer-data boundaries

Evidence: `apps/api/src/trpc/routers/sales.route.ts` still exposes public procedures with write or payment behavior, including `createStep`, `salesPayWithWallet`, `startNewSales`, `resolvePayment`, `restore`, `saveSupplier`, `deleteSupplier`, and `updateStepMeta`. `apps/api/src/trpc/routers/checkout.route.ts` exposes public checkout and quote-acceptance actions. `apps/api/src/trpc/routers/customer.route.ts` exposes `getCustomerPayPortal: publicProcedure`.

Inference: some public procedures may depend on token checks inside query helpers, but the route declarations make the trust boundary hard to audit and train. Money movement, customer pending sales, supplier records, and sales restoration should have explicit route-level authorization or signed, purpose-scoped token contracts.

Operational risk: mixed-skill teams need simple accountability. Public money-side routes make it harder to answer "who did this, under what permission, and why" when a customer payment, quote acceptance, or restored sale is disputed.

### P1 - Monorepo typecheck is blocked by shared package module-resolution drift

Evidence: `packages/settings/tsconfig.json` uses `module: "NodeNext"` and `moduleResolution: "NodeNext"`. `packages/errors/src/index.ts` exports internal modules using extensionless relative specifiers, which triggered TS2835 in `@gnd/settings`.

Operational risk: this is not directly a warehouse or sales workflow bug, but it removes a key safety net for every surface that imports shared platform packages. The failure moved from `@gnd/email` to `@gnd/settings`, so the codebase is making progress in one area while exposing another packaging contract mismatch.

### P1 - Inventory correctness is still not release-clean and repair work remains stopped

Evidence: Brain inventory cutover files still record open reconciliation/backfill evidence and explicit repair stoppage by user request. No repair dry-run or apply command was run in this automation, per instruction.

Operational risk: in door manufacturing, inaccurate stock, stale allocation, or missing sales coverage can cascade into bad promises, avoidable purchasing, production delays, and delivery disappointment. This should remain a release gate until Brain records clean evidence.

### P2 - Dealer order guidance is clearer, but not manufacturing-readiness specific

Evidence: `apps/dealership/src/lib/dealer-next-step.ts` summarizes states as `preparing`, `ready`, and `completed`. `apps/dealership/src/components/dealer-portal/dealer-order-overview.tsx` shows progress around order approval, customer payment, GND payment, and fulfillment.

Inference: the dealer surface does not yet appear to explain dimension, hinge, swing, profile, material, production, or loading blockers in dealer/customer language.

Operational risk: dealers will ask office staff for updates when the product says "preparing" but not "what is blocking this door." This increases calls, rework, and unclear accountability.

### P2 - Mobile packing quantity work is less recoverable than dispatch proof work

Evidence: `apps/mobile/src/features/dispatch/components/dispatch-detail-screen/hooks/use-packing-slip-drafts.ts` stores packing quantity drafts in component state and resets from packable items when opened. By contrast, `apps/mobile/src/features/dispatch/lib/dispatch-proof-draft-storage.ts` persists proof drafts with AsyncStorage/FileSystem and attachment staging.

Operational risk: warehouse and driver users are interruption-heavy. Quantity entry that is easy to lose on restart or navigation is a practical accuracy risk, especially for teams with varying technical comfort.

## Worker Usability Review

The strongest current direction is that driver/dispatch proof is moving toward explicit request IDs, manifest revisions, attachment staging, and recoverable proof states. That model fits real field work better than a desktop-style form.

The weakest worker experience remains around unclear boundaries and inconsistent recovery. A warehouse user should not have to infer whether quantity drafts survive a restart. A sales or office user should not have to know which public procedure has hidden token validation and which one is a true internal action. A production user needs readiness language tied to door manufacturing facts, not only generic fulfillment state.

Good worker-facing improvements already tracked in Brain include the Sales Production Worker Workspace Modernization, Driver Dashboard Command Center, Fulfillment V2 parity, and mobile invoice save reliability work. Today's review did not find enough evidence to treat those as complete release gates.

## Customer And Dealer Experience Review

The dealer experience has improved through next-step guidance and quote/order structure, but it still reads more like a payment and fulfillment tracker than a manufacturing readiness tracker. Dealers and customers need plain reasons for delay: missing measurement, hinge/swing conflict, profile unavailable, material shortage, payment hold, production not assigned, packed but not loaded, or out for delivery.

The customer payment portal remains a concern because `getCustomerPayPortal` is public and account-identifier driven. It returns pending sales, wallet/payment context, terminal context, and customer details. Even if this is intended for a lightweight pay link experience, the contract should be signed, expiring, scoped, and clear enough that customer-service staff can explain it.

## Door-Manufacturing Workflow Gaps

- Manufacturing readiness is still not consistently surfaced across sales, dealership, customer status, production, and dispatch.
- Inventory correctness remains a hard blocker for reliable production promises and purchasing decisions.
- Mobile packing is not yet scan-first, and quantity drafts do not appear to have the same persistence model as proof drafts.
- Dealer fulfillment status is too coarse for doors with configurable dimensions, swing, hinge, profile, material, shop stage, packing, loading, and delivery handoff.
- Payment route boundaries remain hard to explain operationally, especially where public route declarations wrap money-side behavior.
