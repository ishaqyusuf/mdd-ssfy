## Highest-Risk Findings

### P1 - Public sales/payment/configuration procedures remain on high-value operational routes

Evidence:

- `apps/api/src/trpc/routers/sales.route.ts:622` exposes `createStep` as a `publicProcedure`.
- `apps/api/src/trpc/routers/sales.route.ts:972` and `apps/api/src/trpc/routers/sales.route.ts:975` expose `getOrders` and `getOrdersSummary` as public reads.
- `apps/api/src/trpc/routers/sales.route.ts:1386` exposes quotes as public.
- `apps/api/src/trpc/routers/sales.route.ts:1398`, `apps/api/src/trpc/routers/sales.route.ts:1403`, and `apps/api/src/trpc/routers/sales.route.ts:1408` expose `salesPayWithWallet`, `startNewSales`, and `resolvePayment` as public mutations.
- `apps/api/src/trpc/routers/sales.route.ts:1454`, `apps/api/src/trpc/routers/sales.route.ts:1459`, and `apps/api/src/trpc/routers/sales.route.ts:1464` expose supplier and sales-step metadata mutations as public procedures.

Why it matters for operations: sales, payments, supplier data, step configuration, and order state sit directly in the revenue and production handoff path. If these routes rely on implicit caller discipline rather than explicit authorization, the system becomes hard to train, audit, and safely expose across dashboard, dealership, mobile, and customer surfaces.

This is related to the completed API public-route hardening work, but it appears to be a remaining sales/payment surface rather than coverage already closed by that plan.

### P1 - Public customer pay portal lookup returns broad order, contact, wallet, and terminal context

Evidence:

- `apps/api/src/trpc/routers/customer.route.ts:58` exposes `getCustomerPayPortal` as a `publicProcedure`.
- `apps/api/src/db/queries/customer.ts:2061` accepts an `accountNo` input and builds pay-portal context.
- `apps/api/src/db/queries/customer.ts:2165` lets pending-sales lookup use either `cust-<id>` or a phone/account identifier.
- `apps/api/src/db/queries/customer.ts:2186` through `apps/api/src/db/queries/customer.ts:2197` returns order id, sale id, order meta, grand total, customer name, email, phone, billing address, amount due, paid amount, and payment method.
- The portal response also includes wallet, total payable, recent payment method, terminal list, terminal error, and last terminal id.

Why it matters for customers: payment is a trust moment. A public account-number lookup that returns rich context makes it easier to leak customer data, display the wrong customer balance, or create support disputes around whether a pay link or terminal state is legitimate.

## Worker Usability Review

- Dashboard operator workflows are improving: recent Fulfillment V2, inbound Needs application, and sales-form step-picker work all aim at clearer actions. The remaining problem is not lack of UI effort; it is that release confidence and inventory correctness are still not clean enough for broad training.
- Inventory/warehouse staff still need a simple manager-readable signal for whether material demand, inbound receipt, allocation, and component recomputation are trustworthy. The reversible Needs work is valuable, but a worker should not need to know audit-event internals to understand whether stock can be promised.
- Drivers/installers need the in-progress mobile proof and dispatch work to converge on a few predictable actions: view manifest, confirm item, capture proof, retry sync, and know what has not synced. The driver platform plan already points in that direction.
- Sales reps using mobile invoice flows need live catalog/product defaults and web parity before the flow is safe to train widely.
- Admin/office users need public route boundaries to be explicit. A workflow is harder to supervise when internal actions work from unauthenticated route declarations and hidden query-layer assumptions.

## Customer And Dealer Experience Review

- The customer pay portal is the most sensitive customer-facing gap. It should not depend only on broad account identifiers while returning rich payment/order/contact context.
- Dealer next-step guidance is useful, but it does not yet answer the operational questions dealers will ask after payment: Are materials ready? Is production started? Is it packed? Is pickup/delivery scheduled? Is there proof?
- Dealer order pages show totals, balances, line items, and documents, but they do not yet expose door-specific readiness checks such as dimensions, swing/hinge/profile validation, production hold reasons, or packing status.
- Customer and dealer communications should converge on the same delivery/pickup status vocabulary as dashboard and mobile. The current state still risks each surface explaining the same order differently.

## Door-Manufacturing Workflow Gaps

- Door configuration readiness is not yet a shared cross-surface contract. Dimension, swing, hinge, profile, quantity, price, production, material, and delivery implications should be validated once and reused by dashboard, dealership, mobile, and documents.
- Manufacturing readiness is still too compressed for dealers and customers. `preparing`, `ready`, and `completed` are not enough to explain material wait, production queue, quality check, packing, pickup, loaded, out-for-delivery, and delivered states.
- Inventory release evidence remains unclean, which limits confidence in allocation visibility, inbound Needs application rollout, and manager oversight.
- Mobile and dealership flows still need stronger proof loops: barcode/scan confirmation where appropriate, photo proof, retry state, last-updated state, and manager-visible exceptions.
- Print/PDF and customer-facing documents should eventually reflect the same readiness/payment/delivery truth as the app surfaces, not a separate approximation.
