## Highest-Risk Findings

- P1 - Public checkout router still owns money and operational side effects. `apps/api/src/trpc/routers/checkout.route.ts` exposes `initializeCheckout`, `initializeQuoteAcceptance`, `acceptQuote`, `createSalesCheckoutLink`, `verifyPayment`, and `generateDeviceCode` as `publicProcedure`. The query implementation validates signed quote/payment tokens for some flows, but the same public router can create orders from accepted quotes, create payment links, verify payments, and generate Square terminal device codes. For door manufacturing operations, this is a customer-trust and revenue boundary: public token flows should be deliberately separated from staff-only payment/device operations.

- P1 - Public customer pay portal lookup returns rich account context from `accountNo`. `apps/api/src/trpc/routers/customer.route.ts` exposes `getCustomerPayPortal` as `publicProcedure`; `apps/api/src/db/queries/customer.ts` accepts only `accountNo`, loads pending sales, wallet, recent payment method, Square terminals, terminal errors, and last terminal id context. The implementation also returns customer names, email, phone, address, order ids, totals, amount due, and payment method for pending orders. Inference: phone-number/account-number guessing could expose customer and balance data unless outer routing or tokenization blocks access elsewhere.

- P1 - Public Square test route is mounted and can create terminal checkouts. `apps/api/src/trpc/routers/square-test.route.ts` defines `squareTest.test` as `publicProcedure` and calls `squareClient.terminal.checkouts.create` with a caller-provided device id. `apps/api/src/trpc/routers/_app.ts` mounts `squareTest`. Even at `$10.00`, this is an avoidable payment-provider side effect on a public route.

- P2 - Task Events has Super Admin query guards but a public route contract. `apps/api/src/trpc/routers/task-events.route.ts` declares list/get/update/history/runNow/runTest/runStatus as `publicProcedure`; `apps/api/src/db/queries/task-events.ts` then calls `requireSuperAdmin` inside each handler. This reduces direct exploitability, but the route declaration is inconsistent with the hardening policy and can confuse future contributors into adding scheduler behavior outside the guard.

- P2 - Repository typecheck remains red at the shared package boundary. The recurring `@gnd/settings` failure means broad validation cannot currently prove cross-package safety. This matters because the current dirty work includes DB, sales lifecycle, dashboard request-control, and schema changes.

- P2 - Active Sessions remains a mock security surface. `apps/dashboard/src/components/user-logged-in-devices.tsx` renders hard-coded device rows and a fake logout delay with `TODO: Implement actual logout logic.` Users may believe device sessions can be inspected or revoked when the app is not enforcing that behavior.

- P3 - Dealer next-step guidance is payment/fulfillment oriented, not manufacturing-readiness oriented. `apps/dealership/src/lib/dealer-next-step.ts` now gives clear payment and pickup/delivery messages, which is good. It still does not expose door-manufacturing blockers such as dimension ambiguity, handing/swing, profile/finish confirmation, material availability, production assignment, packed quantity, or document readiness. This is a usability gap rather than an auth defect.

For warehouse users under interruption or weak connectivity, durable quantity recovery remains less explicit than delivery proof recovery.

## Customer And Dealer Experience Review

Customer-facing payment and quote acceptance flows need a cleaner split between public token experiences and internal payment/device actions. Public quote acceptance can be appropriate with signed tokens, but public payment-link creation, payment verification, device-code generation, and account-number pay portal lookup are too broad to leave grouped together without a visible route-boundary contract.

Dealer guidance is more trainable than before: approved, rejected, balance-due, preparing, ready, and fulfilled states are readable. The missing layer is manufacturing confidence. A dealer should know whether the order is truly build-ready before telling a customer it is moving, especially for size, hinge/swing, profile, finish, material, and document proof.
