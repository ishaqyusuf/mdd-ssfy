## Highest-Risk Findings

### P1 - Public Square test route can create real terminal checkouts

Evidence: `apps/api/src/trpc/routers/square-test.route.ts` exports `test: publicProcedure` and calls `squareClient.terminal.checkouts.create(...)` for a fixed `$10.00` amount using caller-supplied `deviceId`. `apps/api/src/trpc/routers/_app.ts` mounts it as `squareTest`.

Impact: this is a direct payment-provider side effect outside the protected checkout/refund/payment permission model. For office staff and customers, accidental or forged requests could create confusing terminal prompts and weaken trust in payment operations.

Inference: this looks like a development/test endpoint that should be removed from the production router or moved behind Super Admin plus environment gating.

### P1 - Remaining public sales/payment/customer-account paths still bypass the route-level operational boundary

Evidence: `apps/api/src/trpc/routers/sales.route.ts` still uses `publicProcedure` for `createStep`, `salesPayWithWallet`, `startNewSales`, `resolvePayment`, `restore`, supplier writes, `updateStepMeta`, broad quotes/accounting/product-report reads, and mobile dashboard overview. `apps/api/src/trpc/routers/customer.route.ts` exposes `getCustomerPayPortal` as public. `apps/api/src/db/queries/customer.ts` resolves pending sales from `accountNo`, returns pending order/payment/contact/address context, wallet balance, Square terminals, and recent payment method.

Impact: revenue, customer trust, and operational accountability are exposed because payment actions and internal sales/configuration writes are not consistently protected at the route boundary. Even where downstream logic may validate parts of the request, the trainable rule for staff and agents should be simple: internal sales/payment mutations are authenticated and permission-shaped.

### P1 - Inventory correctness is still not release-clean while repairs remain stopped

Evidence: `.brain/plans/2026-07-01-inventory-system-correctness-cutover-plan.md` and `.brain/tasks/in-progress.md` say repairs are stopped by user request. The latest recorded read-only refresh reports `21745` missing sales, `50` stale lines, `5` componentless lines, `281` reconciliation drifts, `14` skipped comparisons, `hasMore=true`, and next cursor `200`.

Impact: production, purchasing, warehouse, and dispatch users can see improved workflows, but the system cannot yet claim reliable inventory-backed readiness. Door shops rely on exact component demand, supplier ordering, allocation, and shipment truth; stale or missing projections undermine manager confidence and can create late material surprises.

### P2 - Typecheck remains red in the email package

Evidence: `bun run typecheck` stops in `@gnd/email` on missing React/JSX declaration types. Recent dispatch, dealer, storefront, payment, and client-notification email templates are operationally important.

Impact: the monorepo cannot be broadly proven by the standard type gate. This increases release risk for email/PDF/customer-communication changes, even if narrower tests pass.

### P2 - Task events use public route declarations with internal Super Admin checks

Evidence: `apps/api/src/trpc/routers/task-events.route.ts` declares list/get/update/history/runNow/runTest/runStatus as `publicProcedure`, but `apps/api/src/db/queries/task-events.ts` now calls `requireSuperAdmin(ctx)` inside each query/run function.

Impact: the direct exploit risk is lower than older reports implied, but the route shape remains inconsistent with the rest of the permission model and easy to regress. Scheduler operations should read as protected at the router boundary.

### P2 - Runtime notification/job logging can expose operational payloads

Evidence: `packages/notifications/src/services/notification-trigger.ts` logs full notification payloads; `packages/notifications/src/index.ts` logs contacts/users and email counts; `apps/dashboard/src/components/modals/new-job/job-submit-button.tsx` logs save variables, form errors, and default values.

Impact: sales/customer/job/payment-adjacent data can leak into local, Vercel, or worker logs. This is especially risky for mixed-skill operations where support screenshots and terminal logs may be shared during troubleshooting.

## Worker Usability Review

- Sales reps have better Sales QA, Sales Finance, Needs Action, production, and dispatch surfaces, but the remaining public sales/payment route shape makes accountability harder to explain and audit.
- Production and warehouse workers now have richer production/packing/driver command workstreams, but inventory cutover evidence is still partial; readiness signals should remain cautious until reconciliation is clean.
- Drivers/mobile workers have improved queue, proof draft, sync-state, and retry handling in the dispatch surface. This is a meaningful improvement for weak-network jobsites.
- Office/admin staff still need a smaller number of obvious, protected commands: pay, release material, assign production, pack, deliver/pickup, and notify customer/dealer. Several flows are implemented locally, but header-level visibility and release proof remain uneven.

## Customer And Dealer Experience Review

- Dealer quote-to-order approval, payment separation, customer/dealer PDFs, and next-step copy are strong and well documented.
- Dealer order detail still presents fulfillment as preparing/ready/complete without exposing door-manufacturing readiness such as dimensions checked, swing/hinge/profile confirmed, material ordered/received, in production, packed, ready for pickup, or delivery scheduled.
- Customer payment self-service still relies on public account-number style lookup for broad payment context. A signed token boundary would be more explainable and safer for customer trust.
- Client-ready status-update documentation exists as an approved plan, but the product still needs surfaced customer/dealer-friendly proof states so reps are not composing status from internal ledgers.

## Door-Manufacturing Workflow Gaps

- Quote/order readiness should expose concrete door checks: size, swing, hinge/handle rules, profile/pricing snapshot, tax/payment method, supplier, and production eligibility.
- Inventory readiness is improving but cannot be treated as authoritative until stopped repair evidence is resolved and clean reconciliation is recorded.
- Dealer and customer views need a manufacturing timeline, not just payment/fulfillment status. Door buyers care whether the order is checked, ordered, built, packed, ready, out, or delivered.
- Mobile packing and dispatch are closer to field-ready, but scan/photo proof should become the default for warehouse load and delivery completion where hardware permits.
- Print/PDF and email remain critical trust artifacts. Typecheck red in `@gnd/email` and runtime logging in notification paths should be treated as customer-communication release risks.
