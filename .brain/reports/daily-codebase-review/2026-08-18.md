## Highest-Risk Findings

**P1 - Generic public task execution can still run arbitrary Trigger jobs and expose run output.**  
Evidence: `apps/api/src/trpc/routers/task-trigger.route.ts:5-20` defines `trigger: publicProcedure` with `taskName: z.string()` and `payload: z.any()`, then passes both directly to `tasks.trigger`. `apps/api/src/trpc/routers/task-trigger.route.ts:21-48` exposes public run status including `output` and `error`. Mobile dispatch and packing still use that public tRPC route for `update-sales-control`: `apps/mobile/src/hooks/use-task-trigger.ts:62-86`, `apps/mobile/src/features/dispatch/api/use-dispatch-packing.ts:81-166`, and `apps/mobile/src/features/dispatch/api/use-dispatch-actions.ts:71-151`. Dashboard uses a separate generic server action that allows any `taskNames` enum value and only special-cases `update-sales-control` metadata/auth stamping: `apps/dashboard/src/actions/trigger-task.ts:15-60`. Inference: these generic paths can bypass or diverge from the stricter route-specific permission checks now present in `apps/api/src/trpc/routers/dispatch.route.ts`.

**P1 - Public task-event scheduler controls can still list, update, run, and inspect scheduled operations.**  
Evidence: `apps/api/src/trpc/routers/task-events.route.ts:18-76` uses `publicProcedure` for `list`, `get`, `update`, `history`, `runNow`, `runTest`, and `runStatus`. These call task-event query/run helpers and return scheduled history/status. Operationally, this is too broad for controls that can alter or run background jobs affecting inventory, payments, notifications, and reports.

**P1 - Payment and Square side-effect routes remain public.**  
Evidence: `apps/api/src/trpc/routers/checkout.route.ts:17-47` exposes `initializeCheckout`, `initializeQuoteAcceptance`, `acceptQuote`, `createSalesCheckoutLink`, `verifyPayment`, and `generateDeviceCode` as `publicProcedure`. `apps/api/src/db/queries/checkout.ts:305-394` returns customer/contact/address/order/payment context from a token; `apps/api/src/db/queries/checkout.ts:784-911` creates Square checkout links; `apps/api/src/db/queries/checkout.ts:931-1195` verifies and applies payment; `apps/api/src/db/queries/checkout.ts:1280-1295` creates a Square Terminal device code with no meaningful input or protected boundary. Customer token routes can be valid public flows, but Terminal device setup and payment mutation paths need sharper server-side capability boundaries.

**P1 - Dashboard cancel dispatch still sends the wrong payload key.**  
Evidence: `apps/dashboard/src/hooks/use-sales-packing.ts:61-72` calls `cancelDispatch.mutate(...)` but sends `startDispatch: { dispatchId }` instead of `cancelDispatch: { dispatchId }`. The same file also has direct generic task-trigger packing paths for clear/pack/reset/complete-all at `apps/dashboard/src/hooks/use-sales-packing.ts:172-255`. For a warehouse/driver workflow, a cancel control that silently starts, no-ops, or misclassifies status creates real dispatch accountability risk.

**P1 - Organization, filter, and HRM read boundaries remain too broad for office/admin data.**  
Evidence: `apps/api/src/db/queries/organization.ts:4-43` exposes organization list and create through `publicProcedure`, and `apps/api/src/trpc/routers/organization.route.ts:7-10` mounts those procedures directly. `apps/api/src/trpc/routers/filters.route.ts:33-124` keeps many internal filters public, including customer, dispatch, employee, inbound, inventory, job, product report, sales orders/quotes/accounting, project unit, and production filters. `apps/api/src/trpc/routers/hrm.route.ts:55-95` exposes employees, drivers, roles, profiles, and permission options as public reads. This conflicts with the office scoping plan and mixed-skill operational expectations.

**P2 - Settings Active Sessions is still mock UI, while the backend has a partial real session query.**  
Evidence: `apps/dashboard/src/components/user-logged-in-devices.tsx:9-24` hard-codes mock devices; `apps/dashboard/src/components/user-logged-in-devices.tsx:35-39` simulates logout and leaves a TODO. `apps/api/src/db/queries/user.ts:550-565` has a real `getLoggedInDevices` query but selects `sessionToken`, which should not be exposed to a client table. This is both a trust issue for office staff and a security hygiene gap.

**P2 - Dealer order detail still lacks manufacturing preflight detail.**  
Evidence: `apps/dealership/src/components/dealer-portal/dealer-order-overview.tsx:258-388` gives next-step, progress, line items, customer/GND payment, and PDFs, while `apps/dealership/src/lib/dealer-next-step.ts:107-178` projects only payment and broad fulfillment states. It does not surface size/swing/hinge/profile/supplier/Special Order readiness or production blockers to the dealer. Inference: dealers will still have to call sales reps for manufacturability questions that the system already partially knows elsewhere.

**P3 - Mobile dispatch proof is stronger, but field proof is still gallery-first and not scan-first.**  
Evidence: `apps/mobile/src/features/dispatch/components/dispatch-complete-form.tsx:111-149` uses `ImagePicker.launchImageLibraryAsync` for optional photos, requires signature, and keeps proof stable for retry. This is good progress, but there is no camera-first/photo checklist, barcode scan, bundle scan, or door-label verification in the live dispatch/warehouse completion flow. For warehouse and drivers, a scan-first path would be more trainable and less error-prone.
