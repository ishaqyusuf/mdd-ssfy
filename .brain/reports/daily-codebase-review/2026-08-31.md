## Highest-Risk Findings

### P1 - Public Square test route can create real terminal checkouts

Evidence: `apps/api/src/trpc/routers/square-test.route.ts:6` exposes `test` as `publicProcedure`; lines `13-24` create a USD terminal checkout for the provided device id; `apps/api/src/trpc/routers/_app.ts:97` mounts it as `squareTest`.

Operational risk: this is a real payment-terminal side effect, not a harmless diagnostic. A public test checkout can confuse sales reps, finance, and customers, pollute Square/device state, and undermine trust in payment workflows.

Tracking label: New candidate.

### P1 - Public task-events controls still expose scheduler operations

Evidence: `apps/api/src/trpc/routers/task-events.route.ts:19`, `31`, `53`, `58`, and `67` keep list/update/runNow/runTest/runStatus on `publicProcedure`.

Operational risk: task events control background operational flows and diagnostics. Even if downstream jobs guard some writes, public run/update/status access makes scheduler behavior harder to reason about and train, especially for non-technical admins.

Tracking label: New candidate.

### P1 - Customer pay portal exposes money/customer context by account number

Evidence: `apps/api/src/trpc/routers/customer.route.ts:58` exposes `getCustomerPayPortal` as `publicProcedure`. `apps/api/src/db/queries/customer.ts:2077-2145` returns pending sales, contact-facing order data, wallet balance, Square terminals, terminal errors, and a last-terminal lookup from `ctx.userId` while accepting only `accountNo`.

Operational risk: account-number/phone lookup is too weak for a customer-facing money surface. It can expose pending invoices, balances, contact details, and terminal context before a signed payment token or authenticated customer session is proven.

Tracking label: New candidate.

### P1 - Monorepo typecheck remains blocked at a shared package boundary

Evidence: `packages/errors/src/index.ts:1-21` uses extensionless relative exports, and `bun run typecheck` fails in `@gnd/settings` with TS2835.

Operational risk: this is not a direct shop-floor bug, but it removes a release gate for settings, guarded packing, sales handoff, print settings, and other shared policy code.

Tracking label: New candidate.

### P2 - Public organization list/create conflicts with office scoping plans

Evidence: `apps/api/src/db/queries/organization.ts:4` and `27` export organization list/create as `publicProcedure`; line `9` lists all organizations; line `21` returns hard-coded `employeesCount: 0`.

Operational risk: office scoping, tenant-readiness, and employee membership training will remain confusing while public organization APIs return incomplete data and allow unauthenticated creation.

Tracking label: Plan exists.

### P2 - Dealer order guidance still hides manufacturing readiness details

Evidence: `apps/dealership/src/lib/dealer-next-step.ts` resolves dealer guidance from order payment state and coarse `fulfillmentStatus` values: `preparing`, `ready`, and `completed`. `apps/dealership/src/components/dealer-portal/dealer-order-overview.tsx` shows Progress as Order approved, Customer payment, GND payment, and Fulfillment, but line items do not show dimension/swing/material blockers.

Operational risk: dealers can see whether an order is preparing/ready, but not whether GND is waiting on door configuration, profile/supplier pricing, materials, production completion, packing, or route scheduling. That creates avoidable calls and missed expectation-setting.

Tracking label: New candidate.

### P2 - Mobile packing quantity drafts are not recoverable like proof drafts

Evidence: `apps/mobile/src/features/dispatch/lib/dispatch-proof-draft-storage.ts:1-124` stores proof drafts in `AsyncStorage` with file staging. By contrast, `apps/mobile/src/features/dispatch/components/dispatch-detail-screen/hooks/use-packing-slip-drafts.ts:32-56` keeps packing quantities in component state only. `apps/mobile/src/features/dispatch/api/use-dispatch-packing.ts:85`, `102`, and `111` generate new request ids at submit/reset time.

Operational risk: proof signatures/photos survive weak connections; packing quantities can be lost on navigation, app reload, or device interruption. Warehouse staff entering LH/RH counts need the same recoverability standard as drivers capturing proof.

Tracking label: New candidate.

### P3 - Active Sessions remains a mock user-facing account feature

Evidence: `apps/dashboard/src/components/user-logged-in-devices.tsx:9` defines `mockDevices`; line `38` still has `TODO: Implement actual logout logic`.

Operational risk: this is lower than payment/inventory risk, but account security UI that appears real while using fake rows can mislead admins during device/security troubleshooting.

Tracking label: New candidate.

## Worker Usability Review

- Production and Fulfillment gained useful operational clarity on 2026-08-30: counted tabs, active/completed split, material-review lifecycle, production stage labels, and worker submission simplification all support trainable workflows.
- The driver web command center is moving toward one-next-action behavior, but pilot gates remain open for weak network/device proof. The product should keep differentiating `saved on device`, `syncing`, `synced`, `conflict`, and `retry required`.
- Warehouse packing still needs recovery parity with proof capture. In door operations, losing a half-entered LH/RH packing slip is a practical error source.
- Active Sessions should either become real or be hidden behind a development/admin flag. Fake device rows are unsafe in an admin/security settings context.

## Customer And Dealer Experience Review

- Dealer quote/order surfaces now have protected portal procedures and meaningful next-step copy. The next customer-experience gain is manufacturing-specific transparency: what is approved, what is being made, what is short, what is packed, and when pickup/delivery can happen.
- The customer pay-portal account-number path is still too broad for a money-facing experience. Payment links should be signed/token-bound, and customer self-service should not depend on guessable phone/account identity.
- Client-ready delivery-status documentation exists, but the product still needs customer/dealer-visible status summaries that do not expose internal diagnostics.

## Door-Manufacturing Workflow Gaps

- Quote/order readiness needs a plain checklist for dimensions, swing/handing, profile/pricing, supplier availability, material readiness, production readiness, packing readiness, and delivery/pickup readiness.
- Dealer order detail should make manufacturing blockers visible without asking dealers to understand internal inventory/projection terms.
- Packing should be scan-first where possible: barcode/QR or SKU lookup, photo exception capture, and clear manager review when counts do not match.
- Inventory release proof remains not release-clean while repairs are stopped. This is the biggest operational correctness gap because it touches stock accuracy, production readiness, fulfillment, and customer delivery promises.
