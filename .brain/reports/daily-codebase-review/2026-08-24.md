## Highest-Risk Findings

### P1 - Public write-capable sales routes still bypass a protected procedure boundary

Evidence: `apps/api/src/trpc/routers/sales.route.ts` still exposes public mutations for `createStep`, `salesPayWithWallet`, `startNewSales`, `resolvePayment`, `restore`, `saveSupplier`, `deleteSupplier`, and `updateStepMeta`.

Impact: these are not just read endpoints. They touch sales workflow setup, wallet/payment resolution, order creation/restoration, and supplier/step metadata. For a mixed-skill operational team, this weakens accountability: office/admin actions should have authenticated actors, explicit permissions, and audit-safe command boundaries.

### P1 - Public task-event scheduler controls remain

Evidence: `apps/api/src/trpc/routers/task-events.route.ts` exposes `list`, `get`, `update`, `history`, `runNow`, `runTest`, and `runStatus` via `publicProcedure`.

Impact: the generic client task trigger improved, but scheduler event update/run controls are still public. Background jobs that affect sales, payments, inventory, reports, or notifications need protected operator commands, not public event-name strings.

### P1 - Monorepo typecheck is red at `@gnd/email`

Evidence: `packages/email/tsconfig.json` extends the shared config; `packages/email/package.json` omits `@gnd/tsconfig`. `bun run typecheck` fails before proving API, dashboard, dealership, mobile, jobs, and shared package integration.

Impact: email is customer/dealer-facing infrastructure. A broken package-level typecheck blocks confidence in sales document email, dealer onboarding/password flows, payment notifications, special-order messaging, and storefront email templates.

### P2 - HRM and filter reads expose operational directories publicly

Evidence: `apps/api/src/trpc/routers/hrm.route.ts` exposes employee, driver, role, profile, permission, and employee overview reads as public procedures. `apps/api/src/trpc/routers/filters.route.ts` exposes customer, dispatch, employee, inbound, inventory, job, product report, sales order, quote, accounting, project, and production filters publicly.

Impact: even where these are read-only, they reveal internal operating structure. For office/admin and mixed-skill workflows, public directories and filters make it harder to reason about role boundaries and future multi-tenant isolation.

### P2 - Inventory is still not release-clean while repair work is intentionally stopped

Evidence: `.brain/plans/2026-07-01-inventory-system-correctness-cutover-plan.md` records the latest read-only evidence as `21745` missing sales, `5` componentless lines, `50` stale lines, `281` reconciliation drifts, `14` skipped comparisons, `hasMore=true`, next cursor `200`, and explicitly says repairs are stopped by user request.

Impact: production, purchasing, warehouse, dispatch, and paid-order handoff all depend on inventory truth. The app can keep shipping incremental improvements, but broad inventory-backed release claims should remain blocked until clean reconciliation and operator proof are recorded.

### P2 - Mobile delivery logic is hardened, but field release proof remains incomplete

Evidence: `.brain/plans/2026-08-23-mobile-delivery-module-logic-hardening.md` is Done for logic but leaves Android/device and screen-level UI review behind explicit approval. The same plan lists weak-network, restart recovery, proof payload, stale notification, and capability-display risks as release concerns.

Impact: drivers, installers, and warehouse workers often operate with weak connectivity and limited patience for complex states. The current direction is correct, but release confidence still needs device proof for "saved on device", retry, stale state, and server-owned action blockers.

## Worker Usability Review

- Production and driver surfaces are becoming more trainable: the Route Command plan answers "what is next, what is blocked, and what can I do" instead of presenting a generic dispatch table.
- Warehouse packing is still too quantity-entry-heavy for lower-friction floor work. The code has server-owned packing and proof improvements, but scan-first verification is not yet a visible first-class workflow.

## Door-Manufacturing Workflow Gaps

- Door configuration readiness is split across internal production/inventory surfaces; dealer/customer wording does not yet expose enough reasoned manufacturing status.
- Inventory cutover evidence is not clean, so material availability, allocation, inbound demand, and dispatch readiness still need release-gate discipline.
- Mobile packing needs a faster physical-world loop: scan item, confirm quantity/handing, capture exception/photo if mismatch, and submit one server-owned command.
- Production worker review has strong foundations, but manager oversight should continue to emphasize exception queues over hidden status transitions.
- Sales and dealership flows should present dimensions, swing/handing, profile, supplier, and readiness checks as a shared vocabulary from quote through production and delivery.
