Inference: recent Brain work closed many dangerous mutation paths, but public internal reads still carry customer trust, staff privacy, production readiness, payroll/payment, and delivery-route risk. For mixed-skill teams, a forged or stale UI state should never become the real access model.

### P1 - Customer pay portal remains account-number keyed and public

Evidence:

- `apps/api/src/trpc/routers/customer.route.ts:56` through `:60` exposes `getCustomerPayPortal` through `publicProcedure`.
- `apps/api/src/db/queries/customer.ts:1626` through `:1640` accepts only `accountNo`, then reads pending sales and wallet data.
- `apps/api/src/db/queries/customer.ts:1697` through `:1710` returns `pendingSales`, `totalPayable`, terminal devices, wallet balance, and recent payment context.
- `apps/api/src/db/queries/customer.ts:1719` through `:1745` lets `accountNo` resolve either `cust-<id>` or a phone number and selects billing contact fields.

This may be intentional for legacy pay links, but today it reads like an enumeration-prone payment surface. Customers and office staff need a smoother portal, but it should be tokenized or authenticated enough that guessing a phone/customer id cannot reveal pending invoices, addresses, wallet state, or device context.

## Worker Usability Review

- Production and dispatch workers benefit from the completed mobile dispatch proof work and production preflight card, but read-side route scoping is still inconsistent with role-shaped workflows. A warehouse or driver UI should never need to rely on hidden buttons to prevent seeing the wrong routes/orders.
- The mobile sales form has many thoughtful parity fixes in Brain, but it is still a large, fragile surface with ongoing save reliability and architecture plans. Mixed-skill sales reps need fewer failure modes around save, customer selection, door/HPT/moulding entry, and quote vs order mode.
- Inventory operators still cannot treat allocation/inbound readiness as fully trusted until the stopped reconciliation work is resolved. The UI can show better readiness cards, but the underlying evidence still says release gates are open.
- Debug logs and mock session UI are small individually, but they teach staff that the system has fake or noisy areas. That erodes training confidence.

## Door-Manufacturing Workflow Gaps

- Production readiness is visible in Sales Overview, but server-enforced start gating remains a separate plan. Door dimensions, handing/no-handle, supplier-price readiness, stock/inbound readiness, delivery/pickup readiness, and PDF readiness should become a consistent release checklist and not only a manager card.
- Inventory allocation/inbound correctness remains the key manufacturing blocker. Door multipliers, HPT child-door mapping, moulding/service/shelf classification, and shipment/allocation drift all need clean evidence or explicit scope decisions before broad production reliance.
- Warehouse and field workflows would benefit from scan/photo-first quick actions: scan a printed pack/route document, see the exact order/line, attach photo proof, and complete the next safe action. Dispatch proof is now strong, but barcode/QR-assisted warehouse picking and pickup handoff are not yet a dedicated implementation item.
- Print/PDF reliability has improved, but `@gnd/www` typecheck still includes sales print service typing failures, so release confidence should rely on focused proof until the broad baseline is clean.
