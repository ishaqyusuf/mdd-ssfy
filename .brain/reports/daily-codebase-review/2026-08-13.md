## Highest-Risk Findings

- P1 - Generic public task execution remains an operational control boundary. `apps/api/src/trpc/routers/task-trigger.route.ts` exposes `trigger` and `status` as `publicProcedure`; `trigger` accepts arbitrary `taskName` and `payload`, and `status` returns output/error details. `apps/api/src/trpc/routers/task-events.route.ts` also exposes list/get/update/history/run controls publicly. Evidence connects this to live workflows: `apps/dashboard/src/components/tables-2/sales-dispatch/columns.tsx` still triggers `update-sales-control` for pack-all completion, while mobile dispatch/warehouse packing still runs packing operations around the same task-trigger pattern. Inference: a trainable warehouse/dispatch workflow cannot be considered manager-accountable while the underlying execution command is generic and public.

- P1 - Public payment and quote-acceptance boundaries still carry rich customer/revenue impact. `apps/api/src/trpc/routers/checkout.route.ts` exposes `initializeCheckout`, `initializeQuoteAcceptance`, `acceptQuote`, `createSalesCheckoutLink`, `verifyPayment`, and `generateDeviceCode` as public procedures. `apps/api/src/trpc/routers/customer.route.ts` keeps `getCustomerPayPortal` public, and `apps/api/src/trpc/routers/sales.route.ts` still has public wallet/payment and sales/accounting read paths. Some public access is expected for tokenized customer flows, but evidence suggests the boundary remains broad enough that payment creation, verification, quote acceptance, and order/payment context need a dedicated signed-token contract and proof matrix before customer-facing rollout confidence.

- P1 - Special-order/non-returnable work is now planned but not enforced in source. The source contains many `"Special Order Only"` labels in `apps/dashboard/src/lib/data/dyke-form-builder.json`, and `.brain/plans/2026-08-12-feature-special-order-acknowledgment-customer-signature.md` correctly calls for declaration, line flags, signature, revision invalidation, and purchasing/production/packing/dispatch gates. Current reviewed source has dispatch/packing signatures and adjustment acknowledgments, but no `specialOrder` order state, customer acknowledgment, signed revision, or package-owned operational release assertion. Operational impact: reps can sell non-returnable sizes/custom work without a system-enforced customer confirmation before purchasing or production.

- P2 - Internal organization, HRM, customer-service, jobs, inventory, and sales read surfaces remain too public for a mixed-skill operations app. Examples: `apps/api/src/db/queries/organization.ts` publicly lists and creates organizations; `apps/api/src/trpc/routers/hrm.route.ts` publicly exposes employees, drivers, roles, profiles, and permission options; `apps/api/src/trpc/routers/customer-service.route.ts` publicly mutates work orders; `apps/api/src/trpc/routers/jobs.route.ts` keeps job reads public; `apps/api/src/trpc/routers/inventories.route.ts` exposes inventory forms/categories/imports publicly; `apps/api/src/trpc/routers/sales.route.ts` exposes orders, quotes, inbounds, accounting, suppliers, and supplier mutations publicly. This overlaps with office scoping and SaaS tenant plans.

- P2 - Active Sessions still presents mock devices and a fake logout. `apps/dashboard/src/components/user-logged-in-devices.tsx` renders hard-coded Chrome/Safari rows and a TODO logout after a timeout, while `packages/auth/src/better-auth/www.ts` and `packages/auth/src/new-device-login.ts` show that device evidence exists elsewhere. This undermines admin trust after new-device and master-password audit work.

## Worker Usability Review

- Sales reps need fewer hidden states around special orders, payment readiness, and downstream release. The new special-order plan is well aimed because it turns a product-label risk into a trainable Yes/No question, line badge, and customer signature.
- Production and warehouse workers have better protected dispatch APIs now, but generic task-trigger completion still makes the execution model harder to explain: the UI says "pack/dispatch", while the backend still accepts arbitrary task names.
- Mobile dispatch proof has improved retry and proof retention, but warehouse packing remains dense and stateful. It would benefit from scan/photo-first quick actions, offline conflict copy, and supervisor-visible exceptions.
- Public HRM/jobs/customer-service route exposure is not just a security issue; it makes permission training brittle because UI roles do not always line up with API enforcement.

## Customer And Dealer Experience Review

- Dealer quote edit locks and next-step guidance are visible improvements. `apps/dealership/src/components/tables/quotes/columns.tsx` disables edits when `editLocked`, and `apps/dealership/src/components/dealer-portal/dealer-order-overview.tsx` shows dealer next-step guidance with payment/PDF actions.
- Dealer quote composition intentionally restricts internal capabilities through `apps/dealership/src/components/dealer-sales-form/adapters/use-sales-form-permissions.ts`, which keeps dealer pricing/payment/dispatch boundaries clearer.
- Customers still depend on public payment and quote acceptance routes for sensitive flows. That is acceptable only if signed tokens, expiration, scope, and audit are consistently proven.
- Special-order acknowledgment is a customer-trust gap until implemented. A customer should see and sign the exact non-returnable items, dimensions, profile/pricing, and total before office release.

## Door-Manufacturing Workflow Gaps

- Production readiness has manager preflight coverage, but dealer-facing manufacturing preflight remains limited; dealers need plain-language checks for door dimensions, swing/handing, hinge/profile/supplier assumptions, special-order status, and payment/fulfillment dependencies before requesting order conversion.
- Inventory correctness remains not release-clean while repairs are stopped by user request. No repair dry-run or apply was run today.
- Warehouse/mobile packing lacks barcode/scan-to-pack proof in active source; design-preview samples mention scans/photos, but production workflows should connect physical item proof to dispatch inventory state.
