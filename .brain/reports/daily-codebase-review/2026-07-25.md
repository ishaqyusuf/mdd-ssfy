## Highest-Risk Findings

- P1 - Internal read/report endpoints remain public after write hardening. Evidence: `apps/api/src/trpc/routers/sales.route.ts` still exposes production lists, production dashboards, sales history, sale transactions, sales resolutions, inbound indexes, order lists, supplier writes, and some dashboard reads through `publicProcedure`; `apps/api/src/trpc/routers/dispatch.route.ts` exposes dispatch indexes, overviews, packing queue/list, deleted dispatch reads, and exports; `apps/api/src/trpc/routers/jobs.route.ts` exposes job lists, payment dashboard/portal, contractor payouts, payout print data, analytics, job overview, and payment overview; `apps/api/src/trpc/routers/hrm.route.ts` exposes employee, driver, role, profile, and permission reads. Inference: even if many consumers are authenticated screens, the route boundary itself does not prove session, role, or ownership, so a mixed-skill shop risks leaking payroll, customer, production, and delivery data.
- P1 - Inventory correctness remains not release-clean. Brain records the latest read-only evidence as `needs_backfill` with large missing-sales scope, stale/componentless lines, reconciliation drift, skipped comparisons, `hasMore=true`, and repairs stopped by user request. This is not a code failure from today's run, but it blocks reliable production readiness, allocation confidence, and manager accountability.
- P1 - Broad WWW typecheck still fails in revenue-critical surfaces. The failing package covers sales form, payment processor, print/PDF, table migrations, task monitor, customer statement, permissions, and shared UI boundaries. Even when focused slices pass, the broad red gate makes it harder to distinguish safe door-pricing/payment/print changes from baseline noise.
- P2 - Customer payment portal read is public and account-number keyed. Evidence: `apps/api/src/trpc/routers/customer.route.ts` maps `getCustomerPayPortal` to `publicProcedure`, and `apps/api/src/db/queries/customer.ts` accepts only `accountNo`, reads pending sales, wallet, recent payment method, Square terminal history by `ctx.userId`, and terminal device data. If this is intended for public customer checkout, it needs token/session semantics documented in the contract; if office-only, it should be protected.
- P2 - Dispatch assigned-read fallback can return unscoped data when unauthenticated. Evidence: `dispatch.assignedDispatch` returns `getDispatches(props.ctx, props.input)` when `ctx.userId` is missing, then scopes to `driversId` only when signed in. That is operationally backwards for a driver app expectation.
- P3 - A storefront helper still has a cost-price pricing TODO. Evidence: `packages/sales/src/storefront.ts` builds `priceList` from `variant.pricing.costPrice` under `//TODO: TRANSFORM COST PRICE BY DEFAULT CUSTOMER PROFILE!`. Recent storefront profile pricing appears implemented elsewhere, so this may be stale/dead code, but it should be removed, retired, or made safe before public launch to avoid future search/filter regressions.

## Worker Usability Review

The product is moving in a better direction for mixed-skill operational staff: dealer quote locks are now server-backed, mobile dispatch completion is a single resumable proof mutation, and packing/warehouse mobile routes exist. Those are trainable workflows because they reduce hidden states and retry confusion.

The remaining usability risk is still accountability by role. Workers can learn "I only see my jobs, routes, packing queue, and production tasks" only if API reads enforce that consistently. Public read routes make it too easy for a UI refactor, mobile screen, or saved filter to show a broader queue than intended. For warehouse, dispatch, HRM, and contractor payment work, route-level ownership is part of the training model, not just a security detail.

## Customer And Dealer Experience Review

Dealer experience improved: Brain records quote-to-order approval as QA-complete and post-request edit locking as done. Dealer next-step copy also accounts for pickup versus delivery states in `apps/dealership/src/lib/dealer-next-step.ts`.

Customer experience still depends on release gates rather than implementation alone. Storefront profile pricing and promotions are implemented, and product-aware shipping quotes are locally implemented, but launch still needs production policy calibration, content/catalog publication, provider rehearsal, and schema/migration history confidence. The customer payment portal contract also needs clarity: account-number-only public reads are convenient, but customers and office staff need a secure, explainable checkout/payment-link model.

## Door-Manufacturing Workflow Gaps

- Production readiness is still gated by inventory correctness. A door shop needs confidence that configured door, HPT, moulding, shelf, and service rows map to available stock, inbound shortages, allocation state, and production/dispatch readiness before work hits the floor.
- Dimension/swing/handing/profile correctness exists in multiple form areas, but the evidence still reads as parity and pricing work rather than one operator-facing readiness checklist. The ideal shop-floor question is: "Can this order be made, picked, packed, and delivered without a manager interpreting hidden state?"
- Product-aware shipping quotes are a strong door-manufacturing fit, especially with long moulding profiles and heavy doors, but remain a release/calibration item rather than a production-ready customer promise.
