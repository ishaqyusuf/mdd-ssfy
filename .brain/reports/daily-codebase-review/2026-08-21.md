## Highest-Risk Findings

### P1 - Public Generic Task Execution Still Crosses Operational Boundaries

Evidence:

- `apps/api/src/trpc/routers/task-trigger.route.ts` exposes public `trigger` and accepts arbitrary `taskName` plus arbitrary `payload`.
- The same router exposes public task `status` with run output and error fields.
- `apps/mobile/src/hooks/use-task-trigger.ts` calls `trpc.taskTrigger.trigger` and `trpc.taskTrigger.status`.
- `apps/mobile/src/features/dispatch/api/use-dispatch-actions.ts` still uses generic `taskName: "update-sales-control"` for dispatch start/cancel flows.
- `apps/mobile/src/features/dispatch/api/use-dispatch-packing.ts` uses the same generic task path for packing updates.

Operational risk:

A generic public task endpoint is hard to train around and hard to audit. In practice, it can blur the line between a driver action, warehouse packing action, admin override, and background automation. Door manufacturing teams need named, permissioned actions such as start dispatch, cancel dispatch, mark packed, and complete proof, with actor and device accountability.

Tracking label:

Already tracked. Prior API route hardening exists, but this remaining generic task-command boundary should be treated as follow-up work rather than a new unrelated initiative.

### P1 - Public Task Event Controls Can Affect Scheduler Behavior

Evidence:

- `apps/api/src/trpc/routers/task-events.route.ts` exposes public `list`, `update`, `history`, `runNow`, `runTest`, and `runStatus`.

Operational risk:

Scheduler controls are manager/admin surfaces. Public access can let non-admin actors inspect or trigger operational automation, which weakens accountability around reminders, production tasks, dispatch jobs, notification jobs, and payment/checkout follow-ups.

Tracking label:

Already tracked. This fits the API route boundary and task monitor work already present in Brain.

### P1 - Broad Public Operational Reads And Legacy Sales Surfaces Remain

Evidence:

- `apps/api/src/trpc/routers/filters.route.ts` exposes public filters for community projects, customers, dispatch, employees, inbound, inventory, jobs, notification channels, products, product categories, profiles, sales, shelves, suppliers, and related entities.
- `apps/api/src/trpc/routers/sales.route.ts` still has many public procedures, including sales history, transactions, resolutions, step components, inbound index, orders, order summaries, quotes, sales pay with wallet, start new sales, resolve payment, restore, product reports, accounting index, sales accountings, mobile dashboard overview, supplier save/delete, and step metadata update.

Operational risk:

Sales, inventory, customers, suppliers, dispatch, and accounting are not just UI filters in a door manufacturing business. They can reveal commercial relationships, production load, customer history, staff data, and payment context. Public route status also makes it harder to explain to office/admin staff which screen is authoritative.

Tracking label:

## Worker Usability Review

Sales and office/admin users now have better payment refund infrastructure and a dedicated fulfillment permission recorded in Brain, but backend route public/private status is still too hard to reason about. A simple UI permission is not enough if older route surfaces still bypass the same accountability model.

Warehouse and driver workflows have better mobile foundations than earlier reports, but the remaining generic task trigger path makes actions feel like implementation plumbing rather than named worker tasks. The product should train workers on concrete operational actions: pack item, flag shortage, start dispatch, capture photo proof, complete delivery, and escalate issue.

Managers need honest status. Mock Active Sessions should either be labeled as unavailable/internal-dev-only or replaced with real session data and real revocation.
