## Highest-Risk Findings

### P0 - Generic public task execution can trigger arbitrary background jobs

Evidence: `apps/api/src/trpc/routers/task-trigger.route.ts:5` defines `taskTriggerRouter`; `trigger` is a `publicProcedure` at lines 6-20, accepts `taskName: z.string()` at line 9 and `payload: z.any()` at line 10, then calls `tasks.trigger(params.taskName, ...)` at lines 15-17. `status` is also public and returns run output/error fields at lines 21-47.

Operational impact: inventory sync, sales control, dispatch packing, email, report, import, and repair-adjacent tasks are accountability-sensitive. A public, stringly typed trigger undermines the stronger dashboard server action boundary, which uses `z.enum(taskNames)` and injects the authenticated actor in `apps/dashboard/src/actions/trigger-task.ts`.

Worker/customer risk: warehouse and driver screens can train users to trust the app's button states, but the real server boundary still accepts arbitrary task names and payloads.

### P0 - Public Square terminal setup/test routes expose payment-device side effects

Evidence: `apps/api/src/trpc/routers/checkout.route.ts:43` exposes `generateDeviceCode` as a `publicProcedure`; `apps/api/src/db/queries/checkout.ts:1280` creates a Square device code with product type `TERMINAL_API` and hard-coded name `GND-MILLWORK-1451`. `apps/api/src/trpc/routers/square-test.route.ts:5` exposes a `publicProcedure` that creates a Square terminal checkout for a caller-supplied `deviceId` at lines 16-30.

Operational impact: terminal pairing and test checkouts are manager/admin controls, not customer checkout controls. Public access risks payment confusion, unauthorized terminal activity, and weak audit evidence if a real terminal is involved.

Brain status: Square payment reliability and terminal production validation are already tracked, but this exact public device-code/test-route hardening appears to be a new candidate.

### P1 - Public task event controls can alter or run operational schedules

Evidence: `apps/api/src/trpc/routers/task-events.route.ts:18` defines the router with `publicProcedure` for `list`, `get`, `update`, `history`, `runNow`, `runTest`, and `runStatus`. The update mutation accepts event status/filter at lines 31-40, and `runNow` is public at lines 53-57. In contrast, task run diagnostics are protected in `apps/api/src/trpc/routers/task-run-diagnostics.route.ts`.

Operational impact: scheduled duplicate cleanup, report dispatch, reminder emails, and operational sweeps should have Super Admin accountability. Diagnostics being protected is useful, but it does not protect schedule mutation or execution.

### P1 - Office organization list/create remains public and unscoped

Evidence: `apps/api/src/db/queries/organization.ts:4` lists all organizations through a public query, and lines 27-44 create organizations through a public mutation. The list returns full organization rows and a placeholder `employeesCount: 0`.

Operational impact: offices are becoming an operational scoping boundary for sales, community, and work orders. Public create/list behavior creates a confusing office model for admins and a future isolation risk for SaaS/office-scoped rollout.

Brain status: Plan exists in `.brain/plans/2026-07-29-feature-office-organization-management-and-scoping.md`.

### P2 - Mobile packing still goes through the generic task trigger path

Evidence: `apps/mobile/src/hooks/use-task-trigger.ts:62` calls `_trpc.taskTrigger.trigger`; line 83 sends caller-provided `taskName` and payload. `apps/mobile/src/features/dispatch/api/use-dispatch-packing.ts:81` configures `taskName: "update-sales-control"` for packing, and `apps/mobile/src/features/dispatch/api/pack-task-payload.ts:13-29` constructs the task payload.

Operational impact: protected dispatch tRPC routes now exist, but mobile packing still depends on the public task trigger. That keeps packing quantity, dispatch status, and actor evidence split across a generic background task instead of a typed, permission-scoped packing command.

Brain status: Driver platform revival closeout and pickup packing funnel workstreams exist, but the public task-trigger replacement should be called out explicitly.

### P2 - Active Sessions is still a mock security surface

Evidence: `apps/dashboard/src/components/user-logged-in-devices.tsx:9-24` defines hard-coded devices, and `logOutDevice` only waits 500ms before a TODO at lines 35-39. The route label says Active Sessions in `apps/dashboard/src/app/(sidebar)/settings/profile/page.tsx`, but the component does not revoke sessions.

Operational impact: users and admins may think they can remove a lost device or stale session, but the control does not perform a real logout. For mixed-skill teams, this is worse than hiding the feature because it teaches a false security workflow.

## Worker Usability Review

- Sales and production workers now have a clearer Special Order flow, including approval history and operation feedback. That is a strong trainability improvement for custom/non-returnable doors.
- Warehouse and driver workflows still mix protected dispatch APIs with a generic public task trigger for packing. The UI can be simple, but the execution model remains harder to explain and audit.
- Active Sessions gives a familiar security affordance but currently uses mock data and no real revocation. Office/admin staff should not be trained on that as a real control.
- Public task event pages and background task controls remain too powerful for routine operators unless protected by route-level roles and clear manager-only affordances.

## Customer And Dealer Experience Review

- Customer Special Order approval now has a real public review/respond flow with signature, decline reason, revision binding, and tokenized access. This directly improves trust for custom door purchases.
- Dealer next-step guidance exists and gives simple status language for approval, payment, and fulfillment. It remains intentionally high-level and does not yet verify door manufacturing readiness before a dealer submits a quote/order request.
- Public checkout and quote acceptance are token-based and customer-facing by design, but terminal device-code generation and Square test checkout routes do not fit that public customer model.
- Dealer order overview clearly separates customer balance from GND balance, which reduces a common dealership confusion point.

## Door-Manufacturing Workflow Gaps

- Dealer quote submission does not appear to include a dedicated manufacturing preflight for door dimensions, swing/handing, hinge/bore assumptions, profile pricing, special-order status, and missing fulfillment data before the quote is sent to GND.
- Mobile warehouse packing still lacks a direct typed packing command tied to inventory allocation evidence. The driver revival plan covers this direction, but today's source still routes packing through `update-sales-control`.
- Special Order is now correctly whole-order, but older catalog labels such as "special order only" still require users to classify the order deliberately. That is acceptable per the feature doc, but training should emphasize declaration responsibility.
- Office scoping is not yet real. If multiple locations manufacture, stage, or dispatch doors, unscoped organization routes and records will keep accountability blurry.
