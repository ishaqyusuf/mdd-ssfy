# Daily GND Codebase Review - 2026-08-11

## Executive Summary

This was a read-only operational codebase review for the GND monorepo. The workspace still has no top-level `brain/` directory, so this report uses `.brain/` as the active project Brain and stores the daily report under `.brain/reports/daily-codebase-review/`. The requested `apps/www` and `apps/expo-app` scope maps to the current `apps/dashboard` and `apps/mobile` workspaces; I reviewed those along with `apps/dealership`, `apps/api`, and the requested shared packages.

The strongest current risk remains operational task control. `apps/api/src/trpc/routers/task-trigger.route.ts` still exposes generic Trigger task execution and run status through `publicProcedure`, while `apps/api/src/trpc/routers/task-events.route.ts` exposes list/get/update/history/runNow/runTest/runStatus through `publicProcedure`. Mobile dispatch start, cancel, and packing still call the generic public `taskTrigger` path, even though `apps/api/src/trpc/routers/dispatch.route.ts` now has protected, assignment-aware dispatch mutations. That leaves two competing operational paths with different safety contracts.

Today also surfaced a concrete dashboard dispatch bug candidate: `apps/dashboard/src/hooks/use-sales-packing.ts` calls the protected `dispatch.cancelDispatch` mutation in one handler but sends a `startDispatch` payload instead of `cancelDispatch`. Runtime wiring was not exercised, but the hook is exported to the dispatch packing overview context, so this should be treated as a high-risk dispatch workflow defect until proven unreachable.

Customer/payment boundary risk remains. `customers.getCustomerPayPortal` is public and account-number keyed, and it returns pending sales, wallet, recent payment method, terminals, terminal errors, wallet balance, and last terminal id. The checkout router still exposes payment initialization, link creation, payment verification, quote acceptance, and device-code generation as public procedures. Some public customer payment entry points are legitimate, but this boundary is too broad for revenue, customer privacy, and fraud-resistant payment handling.

There is also a Brain/source contract mismatch around sales order adjustments. `.brain/features/in-form-sales-order-adjustments.md` describes customer approval links and token-scoped customer approval, while the current source intentionally uses authenticated sales-representative approval without a customer link and has a regression test asserting that no customer approval link exists. This may be an accepted product pivot, but the Brain and UI language need to be reconciled before operators are trained.

## Highest-Risk Findings

### P1 - Generic public Trigger task execution is still an operational back door

Evidence:
- `apps/api/src/trpc/routers/task-trigger.route.ts` exposes `trigger` and `status` as `publicProcedure`.
- The input accepts `taskName: z.string()` and `payload: z.any()`, then calls `tasks.trigger(params.taskName, payload)`.
- `status` returns run output and error details.
- `apps/mobile/src/hooks/use-task-trigger.ts` calls `_trpc.taskTrigger.trigger` and `_trpc.taskTrigger.status`.
- `apps/mobile/src/features/dispatch/api/use-dispatch-actions.ts` uses that hook for `update-sales-control` start/cancel.
- `apps/mobile/src/features/dispatch/api/use-dispatch-packing.ts` uses that hook for dispatch packing.

Impact:
Drivers, warehouse workers, and managers now have protected dispatch APIs available in `apps/api/src/trpc/routers/dispatch.route.ts`, but mobile critical actions still bypass that typed route boundary. This is a revenue and inventory-accuracy risk because dispatch start/cancel/pack changes can move physical work state and inventory readiness.

Inference:
I did not make a network request to prove unauthenticated external exploitability. The risk is based on tRPC route type, lack of `protectedProcedure`, generic task-name input, and live mobile callers.

### P1 - Task Events scheduler controls remain public

Evidence:
- `apps/api/src/trpc/routers/task-events.route.ts` exposes `list`, `get`, `update`, `history`, `runNow`, `runTest`, and `runStatus` as `publicProcedure`.
- `runNow` accepts an event name plus arbitrary filter object.
- `update` can change event status and filter.
- `apps/dashboard/src/app/(sidebar)/task-events/_components/task-event-detail.tsx` calls these task-event run/update APIs.

Impact:
Scheduled inventory, payment-report, duplicate-sweeper, and notification workflows need clear Super Admin accountability. Public update/run controls create an audit and operational reliability gap even if the page itself is hidden by navigation.

### P1 - Customer pay portal and checkout routes expose broad payment context publicly

Evidence:
- `apps/api/src/trpc/routers/customer.route.ts` exposes `getCustomerPayPortal` as `publicProcedure`.
- `apps/api/src/db/queries/customer.ts` takes only `accountNo`, loads pending sales, wallet, recent payment method, Square terminals, terminal error state, wallet balance, and last terminal id.
- `apps/api/src/trpc/routers/checkout.route.ts` exposes `initializeCheckout`, `initializeQuoteAcceptance`, `acceptQuote`, `createSalesCheckoutLink`, `verifyPayment`, and `generateDeviceCode` as `publicProcedure`.
- Dashboard pay portal callers derive `accountNo` from phone/customer id in customer overview and payment processor surfaces.

Impact:
Phone-like customer account identifiers are trainable for staff, but weak as public access control. This can expose customer balances, pending order/payment context, and terminal-related operations across a customer service surface that directly affects cash collection.

### P1 - Dashboard dispatch cancel handler sends the wrong payload shape

Evidence:
- `apps/dashboard/src/hooks/use-sales-packing.ts` `onCancelDispatch` calls `cancelDispatch.mutate(...)` but passes `startDispatch: { dispatchId }` instead of `cancelDispatch: { dispatchId }`.
- The same file has a separate `onUnstartDispatch` handler that passes the expected `cancelDispatch` payload.
- `apps/dashboard/src/components/dispatch-packing-overview/index.tsx` consumes the `PackingProvider` context, but today I did not prove which specific UI action uses the bad handler.

Impact:
If this handler is reachable, a dispatcher trying to cancel or mark an issue could get a no-op or mismatched task response while the truck/work state remains active. For mixed-skill operations, this is exactly the kind of silent state mismatch that leads to missed deliveries, double calls to customers, and inventory/driver accountability confusion.

### P2 - Adjustment approval product contract is inconsistent across Brain and source

Evidence:
- `.brain/features/in-form-sales-order-adjustments.md` says release one creates an expiring customer approval link and approval tokens are random, expiring, and hash-stored.
- `.brain/plans/2026-08-04-sales-quantity-reduction-wallet-credit.md` includes a public customer approval experience as a core phase.
- `apps/dashboard/src/components/forms/new-sales-form/new-sales-form.tsx` now submits committed changes as “Sales representative approved...” and immediately starts the adjustment flow.
- `apps/dashboard/src/components/forms/new-sales-form/sections/sales-change-review-sheet.test.ts` explicitly asserts the UI does not contain “Create customer approval link”, “Copy approval link”, or “Customer contact reference”.
- `apps/api/src/trpc/routers/new-sales-form.route.ts` still contains public approval endpoints, which may be dormant or used by another path.

Impact:
The source may be correct, but Brain and training language currently suggest a customer-approval workflow. Sales reps, finance, and customer service need one truth because wallet credits, quantity reductions, and irreversible production/inbound commitments affect customer trust and auditability.

### P2 - Organization API still contradicts office and tenant scoping plans

Evidence:
- `apps/api/src/db/queries/organization.ts` exports `getOrganizationProfile` and `createOrganizationProfile` as `publicProcedure`.
- `getOrganizationProfile` returns all organizations with `findMany({})`.
- `createOrganizationProfile` creates a row from a name and primary flag, then returns `{}`.
- `packages/db/src/schema/organization.prisma` has no tenant parent, status, or membership shape.
- `.brain/plans/2026-07-29-feature-office-organization-management-and-scoping.md` explicitly requires organization routes to move off `publicProcedure`.
- `.brain/plans/2026-08-08-feature-multi-tenant-saas-commercialization.md` and ADR-052 say `Organization` must stay an office/location inside `Tenant`, not become a tenant boundary.

Impact:
This is a blocker for any office-scoped reporting, staff assignment, and future SaaS pilot work. It also risks confusing staff because “Office” is visible in employee/profile areas but not enforced as an authoritative scope.

### P2 - Active Sessions still shows mock devices and fake logout

Evidence:
- `apps/dashboard/src/components/user-logged-in-devices.tsx` defines `mockDevices` for Chrome/macOS and Safari/iOS.
- `logOutDevice` waits `500ms`, has `TODO: Implement actual logout logic`, and does not revoke a session.
- The auth packages now expose real session metadata and new-device detection, so the raw materials exist.

Impact:
For office/admin staff, a visible “Active Sessions” table that cannot revoke sessions is worse than no control. It trains admins to believe a security action happened when it did not.

### P2 - Broad public read/filter surfaces still expose operational data shape

Evidence:
- `apps/api/src/trpc/routers/filters.route.ts` has public filters for community projects/templates, customers, dispatch, employees, inbound, inventory, jobs, sales reports, sales orders, quotes, accounting, production, and unit work.
- `apps/api/src/trpc/routers/hrm.route.ts`, `jobs.route.ts`, `community.route.ts`, `inventories.route.ts`, `sales.route.ts`, and `print.route.ts` still contain numerous public reads.

Impact:
The prior operational mutation hardening is valuable, but query/filter/read endpoints still shape sensitive operational data for sales, production, HR, jobs, dispatch, community, and finance surfaces. This becomes higher risk if the SaaS tenant plan proceeds.

## Door-Manufacturing Workflow Gaps

- Dealer manufacturing preflight: there is no obvious dealer-facing pre-request checkpoint that validates dimensions, LH/RH, hinge/swing/handing, profile, tax/price profile, hidden dealer components, pickup/delivery mode, and production/inventory readiness in one checklist.
- Dispatch execution source of truth: protected dispatch APIs consume inventory and proof completion, but mobile packing/start/cancel still leans on generic task execution. Door manufacturing needs traceable physical handoff, not two parallel command paths.
- Barcode/scan-to-pack: mobile and design previews mention scan/barcode concepts, but the live dispatch/warehouse flow reviewed today still appears touch/manual-first. This is workable for v1, but scan/photo proof would reduce wrong-door and wrong-side pickup errors.
- Inventory correctness: Brain still says reconciliation is not release-clean and repairs are stopped. No repair dry-run/apply was run today. Any production readiness or fulfillment confidence should keep this caveat visible.
- Post-sale adjustment authority: reductions can affect inbounds, production quantity floors, delivered quantity, wallet credit, and customer expectations. The implementation needs one authority model and one training story.
