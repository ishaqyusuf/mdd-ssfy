# ADR-053: Revision-Bound Special Order Approval And Operational Enforcement

- Status: Accepted
- Date: 2026-08-13
- Related plan: `.brain/plans/2026-08-12-feature-special-order-acknowledgment-customer-signature.md`
- Related feature: `.brain/features/special-order-acknowledgment.md`

## Context

GND needs customer acknowledgment for non-returnable Special Orders without
adding fragile flags throughout nested product configuration. Approval must be
provably tied to what the customer reviewed, cannot be reusable, and must govern
multiple purchasing, production, packing, and dispatch entry points consistently.

## Decision

1. Special Order is a whole-order declaration, separate from the general Sales
   lifecycle status and never inferred from item text or product type.
2. Approval is valid only when an immutable approved evidence row matches the
   order's current deterministic Approval Revision. `SalesOrders` current
   pointers are conveniences, not sufficient evidence by themselves.
3. Public approval uses a random capability whose SHA-256 hash alone is stored.
   The request is scoped to one order/revision/policy version, expires, and is
   atomically consumed by the first approve or decline response.
4. Published policy versions and approval evidence are immutable. Material
   changes supersede evidence and revoke outstanding requests while preserving
   history.
5. A package-owned, server-authoritative gate reads fresh order, current
   evidence, and global Sales settings at every governed operation. It applies
   the shared Warning Only / Block Purchasing & Production / Block All matrix
   to API, direct command, batch, automation, and worker entry points.
6. Recovery operations such as cancellation, release, rollback, and
   reconciliation bypass forward-progression blocking.
7. Customer documents may carry policy and signature evidence; operational
   documents expose compact status only.
8. A governed order requires a valid canonical customer email before manual
   save. One reusable Midday-style dialog updates `Customers.email` and resumes
   the interrupted classification/save/send only after success; the server
   independently fails closed. No duplicate order-level email field is added.
9. Signature PNGs are encrypted with an authenticated AES-256-GCM envelope
   before Blob upload. Production defaults to private Blob access; local stores
   that do not support private objects may explicitly use public access because
   only ciphertext is exposed. The Blob URL is not persisted. Decryption occurs
   only in the authenticated order-view route.
10. Migration-chain exception: the repository's required `bun run db:migrate`
    workflow was attempted first, but the pre-existing split migration roots and
    shadow replay failure at `20260722180000_master_password_usage_audit`
    prevented Prisma from generating the additive feature migration. The legacy
    migration remains unchanged in its original root. A compatibility copy was
    placed in the active root, and the Special Order migration was generated by
    Prisma schema diff, inspected as additive-only, applied only to local MySQL,
    and reconciled in the local migration ledger. This exception does not
    authorize hosted writes or future manual migrations; repair of the split
    chain remains separate prerequisite work.
11. Capability creation, hashing, JSON coercion, issuance, revision comparison,
    enforcement, and direct customer/address invalidation are package-owned.
    API modules remain integration adapters for authenticated context, Blob,
    notifications, email-ledger persistence, and tRPC error mapping.
12. Concurrent or repeated valid responses converge on the already-completed
    terminal result. The transaction loser re-reads committed evidence instead
    of returning a conflict that contradicts the single-use public contract.

## Consequences

- A copied or stale database pointer cannot make an approval current without
  matching immutable evidence.
- Approval links are safe to include in email but cannot be reused after a
  response or after an order revision changes.
- Stronger enforcement can be enabled centrally without redeploying, while
  Warning Only supports a low-risk launch.
- Every new purchasing or fulfillment command must explicitly declare its
  operation category or remain a recovery-only path.
- The schema is additive and leaves legacy null declarations unmanaged; no
  backfill guesses historical intent.
- Customer email repair reuses the existing customer record and mutation, so the
  extension requires no additional database migration.
- Signature confidentiality does not depend on the Blob store access tier. The
  server encryption secret becomes required in production (with the existing
  Special Order/auth secret chain as the supported fallback), and key rotation
  requires an explicit re-encryption plan for historical envelopes.
